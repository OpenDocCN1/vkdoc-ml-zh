# 5. 模型可解释性中的人为因素

前几章讨论了可解释性方法的属性和评估标准；然而，请记住，解释是为人类设计的。因此，设计解释时的人为因素非常重要。

解释系统及其实现的几个主要组成部分涉及目标、策略和流程。本章将从人类的角度涵盖所有这些内容。我们引用了一些实际从业者提供的例子。^(¹)

就像任何需要影响业务的机器学习实践一样，可解释性也需要公司内不同角色的人员之间的合作和头脑风暴。这建立起了对可解释系统的信任。这种信任不仅限于人与模型之间的信任，常规互动也能在组织内部人员之间建立信任。

让我们从讨论可解释性角色开始。

## 可解释性角色

可解释性实践的利益相关者可以分为三大类：技术专长构建者、领域知识审查者和模型消费者。

### 技术专长构建者

这些角色通常由组织内的数据科学家或机器学习工程师担任。这些人开发、设计或测试模型，并将系统集成到组织的数据基础设施中。

### 领域知识评审员

评审员是一个有趣的分类。这些人拥有领域知识，其重要性仅次于技术专家。他们与专家合作，为模型提供反馈，并确保模型达到预期目标且行为符合预期。这些人可能具备也可能不具备机器学习的（ML）技术知识。评审员提供不同的视角来修复潜在问题。评审员类别可能非常广泛；因此，将其进一步细分为更具体的角色是有益的。

*   **领域专家**：领域专家对模型需要捕捉的现实世界现象有深刻的理解。例如，医疗产品中的医生或信用评估模型中的分析师。

*   **产品经理**：产品经理负责开发组织所需的实际产品。需求和业务目标是产品经理的主要沟通议程，他们还确保所有目标按时达成。

*   **审计员**：审计员从法律角度审查模型。他们的目标是确保模型从合规性角度满足法律要求。

### 利益相关者或最终用户

利益相关者是模型所提供信息和决策的最终用户。这个群体包括以下人员：

*   使用`死亡率和再入院模型`的医生
*   使用`贷款审批模型`来决定是否批准贷款的银行代表
*   必须预测机器何时会故障或输出模式可能为何的工程师
*   可能想了解药物效果的生物学家

这些人可能属于也可能不属于技术专家或评审员所在的公司。这取决于组织的商业模式。对于为其他组织提供机器学习（ML）服务的服务型公司，利益相关者通常属于客户组织。对于进行内部机器学习（ML）咨询的公司，利益相关者则属于同一组织内的不同团队。

关于这些角色，需要牢记的一个重要方面是，它们不一定定义单个个体。一个人可以承担多个角色，而一个单一角色可能适用于一个人或整个团队。

## 可解释性阶段

在模型和产品开发的不同阶段，可解释性都扮演着重要角色。

让我们从人的角度来谈谈各个阶段，以及可解释性如何融入这些阶段。

### 构思与概念化阶段

即使在实际模型开发之前，可解释性也扮演着重要角色。在构建模型之前，个人会花费大量时间探索策略和指标。

技术专家可能会邀请领域评审员协助进行特征集的设计阶段，以选择从领域知识角度来看有意义的特征。例如，金融专业人士知道，在定义信用评估模型的特征时，尽早引入业务分析师的视角非常重要。

同样，一些技术专家和审计员会在流程的早期阶段（尤其是在高度监管的行业）合作，定义一个框架来解释每个特征、它是如何设计的，以及为什么使用它不会带来违反法律的风险。一家大型银行的数据工程师解释说，与合规团队一起设计特征，可以更容易地在后续的验证和确认阶段获得他们的信任。

### 构建与验证阶段

在这个阶段，技术专家构建并验证模型。他们运用各种可解释性技术来理解模型为何给出特定输出。这是模型可解释性分类法中应用量最大的阶段。技术专家会选择一种可解释的方法来解释特定的观察结果或模型的整体行为。同时，在构建模型和进行验证步骤时，也会选择模型特定或模型无关的方法。

作为这项活动的补充，技术专家会识别边缘情况，通常称为`异常`或`角落案例`——即模型特别不确定或可能表现异常的情况。即使范围和完整性有限，围绕案例进行推理也是专家们解释和测试`黑盒模型`的常用方法。

此外，专家们还会将模型中使用的特征作为可解释性视角的一部分进行调查，以更好地理解模型。专家们主要通过查看哪些特征驱动了大多数决策，来评估模型的可持续性和合理性。这通常通过按重要性对特征进行排序来完成。在这种情况下，检查不太重要的特征与检查更重要的特征同样有益。

关于特征重要性的信息通常会与其他利益相关者共享，并帮助他们推理模型的行为方式。技术专家还强调，可解释性使得多个模型的比较变得非常容易。可解释性不仅适用于理解单个模型，还可以开发出一组可比较和优化的演进模型。尽管对许多用户来说，模型可解释性是首选的模型比较方法，但目前还没有建立完善的方法论来做到这一点。

在这个阶段，存在两个可解释性需求。

*   **获得信心**。技术专家需要对他们构建的模型的可靠性和有效性建立信心。
*   **获得利益相关者的信任**。当模型是`黑盒`且逻辑过于复杂时，模型利益相关者有时会犹豫是否使用模型来做最终决策。对他们来说，建立信任变得困难。这个问题在高风险环境中尤为严重，因为即使是一个错误也可能导致代价极其高昂的后果。

一位从事重症监护室（ICU）模型工作的高级数据科学家评论道：“我认为我们无法仅靠提供一个`黑盒模型`就蒙混过关。我认为这不会像人们说的那样有效。如果你不向他们（模型使用者）解释清楚，我认为他们永远不会想使用它。”

除了模型分析和验证的需求外，模型技术专家还迫切需要向其他利益相关者传达模型的行为方式、他们可以在多大程度上信任模型，以及在什么条件下模型可能会失败。沟通的质量很重要；它能激发可用于改进模型和获得组织信任的见解。不同利益相关者之间的沟通通常是迭代的，并可能促使进一步的建模工作，以捕捉关于模型运行情况的见解。

模型技术专家描述的最强烈的需求之一是设计方法和工具，以便与模型评审员进行互动和沟通。使用评审员能够理解的语言和表现形式让他们参与到验证过程中，是主要挑战之一。

许多人还相信存在一种“知识的诅咒”；模型技术专家通常难以识别其他利益相关者不知道什么。即使他们掌握了利益相关者的知识水平，确定如何传递这些见解似乎也很困难，即使借助可视化手段也是如此。

### 部署、维护与使用阶段

当技术专家经过多次评审和优化最终确定模型后，通过将模型集成到实际数据流中进行部署。在集成阶段，可解释性问题不仅限于理解模型行为，还扩展到模型周围的整个基础设施。

关于可解释性的目标可能存在一些混淆，即它是为了理解模型如何工作，还是理解整个模型管道如何工作。然而，模型所处的生态系统与模型本身同等重要。在这些场景中，由于模型的黑箱特性以及作为软件一部分的复杂管道，可能会产生可解释性问题。模型框架内信息流的复杂性也可能导致可解释性问题。

在机器学习系统的生命周期中，可解释性挑战出现在模型投入生产之后。一些相关的问题包括：如何检查那些未能反映最新行为的实例/预测模式，以及当模型在支持高风险决策时出现不可接受的错误时，如何查明原因。这类问题由负责监控模型的团队发现。一旦识别出错误，就需要判断是否需要使用可解释性方法来确定错误原因。这种“根本原因分析”可能极具挑战性。

数据科学家通常需要构建更优版本的机器学习模型，因为从先前版本中学习到的新版本可能会提升性能。在这种情况下，模型比较成为可解释性的一部分。在复杂系统中部署多个模型时，不同模型之间的比较通常需要工具的支持。由于模型变更会影响可解释性，模型技术专家需要密切关注模型的参数。有时，专家会保持模型输入不变，以了解变更对不同模型可解释性的影响。

在两种主要情况下，解释至关重要。在高风险情境中，解释发挥着非常重要的作用。例如，当医生使用模型来辅助制定患者决策时，他们需要理解模型是如何“推理”的，以便将其与自身知识相协调。

同一家公司的高级数据科学家指出，有时仅仅解释预测结果是不够的，医生们倾向于了解哪些患者信息可以被操纵，从而使模型产生不同的行为。当模型的使用者同意模型的决策时，解释可以作为支持决策的证据；或者，在模型与人类预测想法不一致的场景中，他们可以从中发现新的见解。在人类不同意模型预测的场景中，可解释性扮演着非常重要的角色。机器学习模型背后的核心理念是，模型应该帮助人类变得更聪明、更高效。但是，当突然出现可能比人类能做出的预测更好的结果，却无法向人类解释时，人类就很难从这些场景中学习，进而提升自己的预测能力或知识。有时，当模型的决策在现实场景中与预期目标相悖时，解释就变得至关重要。

这类场景的一个典型例子是，银行使用模型来支持与客户会面的代表。

一家负责企业信用评估的银行人工智能负责人提到了在组织中解释至关重要的两种主要情况。首先，当客户的贷款被拒绝时，代表需要给出理由（“解释权”是许多国家法律的一部分）。其次，代表们对批准更多贷款有强烈兴趣；因此，他们总是在寻找可以据此采取行动的解释，例如那些能说明如何将拒绝的贷款转变为批准的贷款的解释。

## 可解释性目标

上一节讨论了不同利益相关者在模型开发的不同阶段可能拥有的具体目标。本节总结了我们所遇到的一系列目标，以便更明确地将目标与角色和流程联系起来。我们确定了三大类可解释性目标。

### 用于模型验证和改进的可解释性

# 模型可解释性

模型开发过程中最重要的活动之一是识别模型问题并找到解决方案来修复它们。模型技术专家和评审员应在模型开发过程中实现这一目标。然而，他们有时也需要输入信息才能有效达成此目标。例如，审计员和法律团队可以帮助专家和评审员在修复任何问题时识别出一套严格的法律要求。验证模型的方法之一是检查模型输出的汇总统计数据；然而，我们还需要在此基础上使用可解释性工具和方法。

有时，模型可以以高精度学习输入和输出之间非必要、无意义的关系。这可能使得领域专家的参与对于正确解释结果变得必要。识别不相关的相关性以及虚假的因果推断，可能需要那些既理解模型又理解其机制的专家参与。这一过程的特点是将模型行为与利益相关者对数据和模型预测实际含义的认知进行对比。

从法律角度来看，需要透明度来确保模型不违反旨在防止歧视性行为的法律法规，例如《公平交易法》或《通用数据保护条例》。当模型出错时，解释为何做出特定决策至关重要。合规性是需要可解释性的主要原因之一。

## 面向决策与知识发现的可解释性

可解释性的核心理念在于辅助决策。对于高风险问题，决策者无法信任或使用那些无法为其建议提供理由的预测。同样，解释需要符合专家的需求以及领域的约束条件。围绕可解释性的一个重要主题是**可操作性**。

因此，可操作性目前是可解释系统最重要的新兴需求。每种可解释性方法都会产生特定的解释；然而，并非所有解释都具有可操作性。一些非常常见的方法能提供良好的解释，但可能仅仅增加了对模型及其行为的了解。然而，可解释性的主要优势之一应在于其提供行动或建议的能力。模型专家需要经过多次迭代才能提出可操作的特征。这有时还需要与评审者和利益相关者进行多次讨论。

一个能够解释其决策的工具的潜力，是促进学习或知识发现的催化剂。例如，在决策支持场景中，当决策者与模型意见相左时，模型的可解释性就变得至关重要。在这种情况下，学习是可解释性的一个重要成果。如果不解释模型为何做出某个预测，人类就无法重新考虑决策或向模型学习。在某些情况下，构建模型并非必然用于决策或自动化，而主要是作为理解数据所描述现象并洞察未来 KPI（关键绩效指标）的工具。其目标是理解哪些特征驱动了性能，而非预测未来的性能。

基于过去使用的系统特征，用户留存模型可以显示用户再次使用服务的可能性。

## 通过可解释性建立信心与获取信任

每位模型专家都认同需要对模型建立信任。调试对于确信模型正常运行至关重要。这种个体层面的信任是迄今为止机器学习可解释性研究的典型焦点。即使在客户或利益相关者不要求透明度的情形下，数据科学家也应作为必要的尽职调查的一部分，深入调查其模型以建立理解和信任。然而，说服他人完全信任一个模型，在可解释性工作中往往占据优先地位。对企业模型构建工作或开发这些模型的团队缺乏信任，可能会阻碍组织内机器学习的应用进展。因此，模型技术专家需要对其模型和流程建立信任，并可能依赖可解释性来说服组织中不同角色的其他人，证明他们的工作提供了价值。

能够简洁有效地解释模型的工作原理及其值得信赖的原因并非易事，尤其因为某些利益相关者可能需要在高度抽象且极少技术细节的层面上理解这一点。可视化方法在可解释性的沟通阶段可以发挥重要作用。对于模型专家而言，将建立信任作为建模目标的高度优先性意味着，他们认为需要构建透明模型或使用模型提取方法，向他人解释特定模型的工作原理。

## 描述可解释性工作的人性化主题

旨在产生新工具或新见解的可解释性研究，主要关注个体与模型之间的交互。可解释性被描述为模型类的一种属性，其基础是它与人类期望或约束（如单调性或可加性）的关系，或是来自领域知识的人类驱动约束，亦或是呈现特定模型结果以使人类理解为何某个标签被应用于某个实例（例如，LIME 或 SHAP）。

我们总结了四个主题，它们不同于我们在前几章中提到的技术性描述。这些描述更以人为中心，探讨人类如何与可解释性协同工作，使模型更有用。

### 可解释性是协作性的

组织中的可解释性意味着利益相关者角色之间的协作以及价值观与知识的协调。这个主题主要通过提及与其他利益相关者群体（如领域专家）的讨论来定义。这些讨论经常发生在构思、模型构建和验证阶段，但也发生在部署之后。围绕可解释性的协作对于改进业务推理和说服利益相关者相信已构建的模型将带来价值至关重要。

可解释性在建立和维护组织内部人员之间信任方面的作用，是其社会性本质的另一个明显体现。

人们对用例和轶事的反应远比对数学的反应要好。因此，在与客户沟通时，应采用可解释性的证明和需求。通常需要解释系统的运作方式，然后给出一些答案。

当公关、技术转让或其他离模型开发较远的团队通过可解释性获得信任时，模型的局限性或约束往往更容易被接受。

内部信任使团队摆脱了对可使用的模型类型或所需监控级别的限制，使得模型可解释性被视为获得某种状态的手段。

有时，可解释性的重要性并不在于它能解释任何决策，而在于仅仅包含可解释性这一行为本身就标志着一种“尽职调查”，这让其他利益相关者或最终用户感到安心。

### 可解释性是过程性的

现有的可解释性描述，例如衡量人类心智模型与机器学习模型之间的不匹配，很少评论可解释性随时间发生的可能性。可解释性是一个持续性的关注点。虽然可解释性在不同阶段可能表现不同（例如，在流程早期作为特征选择，与部署后识别模型对现有决策流程的影响），但它自然与一系列可能演变或同时发生的实践和意图相关联，而这些都共同促进了对可解释性含义的理解。

可解释性可以促进人类用户与模型之间的“对话”，这种对话被认为是在模型生命周期内维持学习和持续使用所必需的。

### 可解释性是心智模型比较

可解释性被认为能在组织中带来的学习和意义建构类型，通常是通过不同利益相关者所持心智模型之间的比较来实现的。这与将可解释性定义为可由个体心智模型与机器学习模型之间的交互来确定的定义形成对比。虽然机器学习模型与人类的比较隐含在许多参与者对可解释性的描述中，但机器学习专家自身对问题的理解如何影响他们追求可解释性的方式是显而易见的。

需要付出相当大的努力来理解最终用户的心智模型，以便为他们的工作提供信息。反思人类决策的各个方面，可以细化并正确看待可解释性的目标。

### 可解释性依赖于上下文

团队构建的可解释性解决方案，在很大程度上取决于其目标用户群体的需求和使用场景。可解释性工作的影响与可能非常复杂的决策基础设施密切相关。

## 可解释性挑战的设计机遇

本节讨论从人类视角实施可解释性时会出现的挑战。

### 识别、呈现与整合人类期望

要识别并整合人类对可解释性的期望，理解和识别边界案例至关重要。这种边界案例的识别可以由一群使用模型的人或单个个体来完成。

以下是将可解释性整合到模型构建过程中的一些益处。

-   它帮助人类清晰地表达在可解释性任务中对预测结果的期望。

-   它帮助人类有效识别他们对系统的期望与实际表征之间的差距。

-   它帮助人类根据发现来调试/改变模型行为。

数据科学家经常参与此类协作工作。能够获取利益相关者对其他不同类型模型的反馈，是模型开发和构建阶段的重要组成部分。

一种有益的方法是开发交互式应用程序，利益相关者或最终用户可以使用这些应用程序有效地提供关于模型使用的反馈。研究人员已经开发出平台来发现预测模型所犯的错误，从而收集一群人的反馈。交互式应用程序和方法能够使领域专家和机器学习专家与模型互动，并分享关于决策过程的知识。

### 沟通与总结模型行为

由于模型在构建阶段是协作性和社会性的，因此在模型交接过程中会发生大量的知识转移。为了识别部署后出现的模型错误，拥有能够捕捉模型与模型接收者之间关系的可视化工具非常有益。简而言之，一个好的模型行为总结能为利益相关者和最终用户理解模型工作原理提供极大的便利，并使开发者能够快速解决模型错误。

这些工具可以与识别边界案例的算法一同开发。

一个重要的关注点是改进那些输出与人类行为或感知不一致的方法。

### 可扩展且可集成的可解释性工具

对于许多可解释性方法而言，并不存在关于集成可解释性工具的最佳实践或指南，因为它们是在学术环境中开发的，而工业界需要迎头赶上在生产级模型任务中使用可解释性的趋势。

工具难以与现有平台集成，因为它们无法适应特定的环境。在某些情况下，问题在于可解释性工具无法适应数据规模。

另一个挑战是，可解释性可以成为比较模型的绝佳工具；然而，并没有多少方法能提供关于模型比较的见解。模型比较的案例包括比较参数、选择特征、时间戳等等。

### 部署后支持

在训练后阶段，需要更好的工具来监控已部署的模型。

可视化工具是监控模型行为的绝佳方式。自动异常检测除了识别潜在的有问题行为外，可能也很有用，前提是能够恰当地指定应保持的关键期望（例如从领域专家那里学习到的期望）。
