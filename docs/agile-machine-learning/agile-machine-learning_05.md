# 5. 积极主动的个体

> *围绕* ***积极主动的个体*** *构建项目。给予他们所需的* ***环境*** *和* ***支持***，并* ***信任*** *他们能够完成任务。* `—agilemanifesto.org/principles`

在必应本地搜索产品的早期，我们有一个相当原始的合并/融合引擎，维护成本高昂且效果平庸。几位日复一日与该融合引擎打交道的同事认为，存在更好的融合方法。现有的融合系统已成为一个“bug 农场”，需要大量工作才能维持其运行。新提出的方法看起来很有前景，但挑战在于如何在继续“维持旧系统运转”的同时，找到时间构建新系统。

幸运的是，整个数据管道采用了组件化和模块化的方式设计，融合引擎具有明确的输入边界（融合引擎读取的一组 XML 文件）和清晰的输出边界（融合引擎写入的另一组 XML 文件）。这使得替换融合引擎成为可能，而不会干扰系统的其余部分。

两位积极主动的个体被授权放下当前系统中的所有工作，自行开发一个新的融合引擎。他们被“隔离保护”——这是一个源自金融领域的术语，在微软用于指代确保被隔离的团队与主团队分离，这样他们在开发时间内无需为支持当前活跃的生产项目而“缴税”。管理层被告知，在新融合引擎开发的 6 个月内，预期进度会放缓。尽管最初的预估比实际所需的 6 个月开发时间更为乐观，但对新项目进度的定期审查表明，一切都在按计划进行。管理层提供了必要的“空中掩护”，为新融合引擎的完成争取了所需的时间。当这两位积极主动的个体接近终点线时，更多团队成员被加入，以协助围绕新融合引擎进行额外的集成工作，使其能够投入生产使用。

旧融合引擎和新融合引擎并行了数周，这暴露了新代码中的错误和问题，并得到了迅速修复。随着新融合引擎输出质量开始超越旧引擎，向新融合引擎的切换顺利完成，本地数据系统中的融合质量得到了显著提升。

但该项目成功的关键因素在于这两位积极主动的个体。他们投入了大量的精力和努力来确保项目成功。他们感到被授权去修复系统中存在的重大问题。这激发了他们的工作热情和动力，并最终带来了成功的项目成果。

## 频繁重写

在必应，我们致力于设计允许频繁重写的系统。这是敏捷团队的一项关键能力——完全有可能抛弃现有的融合系统并编写一个新的，因为它与数据管道的其他部分松散耦合。此外，重写一个新系统并与旧系统并行运行（即所谓的 A/B 测试）也很容易，以确保新系统能够像旧系统一样成功运行，并达到相同或更高的质量水平。

Fergus Henderson 在其论文《谷歌的软件工程》中指出，出于类似原因，谷歌试图每隔几年重写其大部分软件：

*这看起来可能成本高得惊人。确实，它消耗了谷歌很大一部分资源。然而，它也具有一些关键优势，这些优势是谷歌敏捷性和长期成功的关键。在几年的时间里，产品的需求通常会显著变化，因为其周围的软件环境和其他技术会发生变化，同时技术或市场的改变也会影响用户的需求、愿望和期望。几年前编写的软件是基于一套较旧的需求设计的，通常无法以最优方式满足当前需求。此外，它通常已经积累了大量的复杂性。重写代码可以削减所有不必要的、针对已不再重要需求的复杂性积累。此外，重写代码是将知识和对代码的“主人翁感”传递给新团队成员的一种方式。这种主人翁感对生产力至关重要：工程师自然会在他们认为“属于自己”的代码上投入更多精力来开发功能和修复问题。频繁重写还能鼓励工程师在不同项目之间流动，这有助于促进思想的交叉融合。频繁重写也有助于确保代码使用现代技术和方法编写。（* [`https://arxiv.org/ftp/arxiv/papers/1702/1702.01715.pdf`](https://arxiv.org/ftp/arxiv/papers/1702/1702.01715.pdf) *）。*

频繁重写能够激励个体，并向他们表明你信任他们。个体在维护那些他们不理解、不是自己编写、也感觉毫无关联的旧代码时，是不会受到激励的。力求频繁重写，以便在你的组织中培养出更多积极主动的个体。



## 寻找并培养积极主动的成员

组织不仅要寻找，更要培养积极主动的成员。首要的人才来源应是组织内部。我们常看到一些组织似乎在系统性地打击员工的积极性。那么，如何确保在现有组织内持续培养出积极主动的成员呢？

培养积极主动成员最关键的一点，或许是设定令人信服的目标、衡量标准和指标——清晰传达团队需要达成的愿景，并提供一套衡量进展的指标——但将"如何实现"的决策权交给团队，更重要的是，要传达出你相信团队能自行找到解决方案。这正对应了宣言中"信任他们能完成任务"的部分。

举个例子，我们曾与一个兄弟团队共事过一段时间。在那个团队中，有一两个人几乎包揽了所有决策权，其他成员只需遵循少数人制定的计划。相比之下，我们的团队鼓励更多人参与讨论，分享最佳想法和策略。我们将"如何做"交给多数人，并信任团队。而另一个团队将"如何做"交给少数人，这并未向其他成员传递信任。由于那个专制团队的领导者非常出色，我们不能说他们不成功——他们确实实施了许多好想法和策略。但我们相信，我们团队的成员感受到更多信任和授权，自然也更有积极性。

对于团队的管理者或领导者而言，一个很好的思考方式是我们称之为"彼得·杰克逊项目管理法"的方法。在拍摄《指环王》系列电影时，彼得·杰克逊对影片的最终效果有清晰的愿景。为了向团队传达这一愿景，他与分镜师合作，制作了覆盖整部电影的分镜图。他说：

> *[分镜图]是电影的低成本预演。我可以用极低的成本——几支铅笔和几张纸——来制作电影，但这实际上让我经历了整个电影制作过程。作为导演，我尝试了，完成了第一版，并能看到完整的电影效果。*

他的制片人巴里·奥斯本补充道：

> *[分镜图]是一个很棒的工具。它从未被当作电影的最终版本。我曾与一些导演合作，他们会绘制分镜图，而你真的会在屏幕上看到那些分镜。彼得不是那种导演。他用分镜图来激发灵感，与各部门沟通，但你知道那些分镜图会改变，对彼得来说，它们是起点，而非终点。*

彼得·杰克逊制作的分镜图帮助团队清晰理解"要创造什么"。但这个"什么"是以低成本方式——简单的铅笔画——呈现的。这个"什么"也被用来让所有人达成共识，但分镜图本质上是低成本、易修改的简单铅笔画，如果行不通或想到更好的主意，可以轻松丢弃。分镜图所代表的轻量级愿景鼓励了团队成员的创造力，计划可以修改，也确实被修改了。但拥有初始计划至关重要。

要将彼得·杰克逊的项目管理方法应用于数据工程项目，就要找到创建"分镜图级别"愿景文档的方法，这些文档易于丢弃、修改，主要用于向团队传达愿景。这些文档通常可以围绕未来的客户体验来构建。例如，你可以描绘客户一年后使用你产品的体验。当团队清晰了解产品一年后的愿景时，他们就能围绕"如何实现"产品愿景而团结起来。通过不向团队强加"如何做"，积极主动的成员自然会涌现，他们不仅能提出创新的"如何做"，还会在发现愿景轻量且开放创新时，感到有权改变"什么"。只需注意将分镜图视为"起点而非终点"。

### 别忘了衡量标准

始终将"分镜图级别"的愿景文档与衡量产品目标的指标相结合。如果本书有一条最重要的信息，那便是"关键在于指标，笨蛋！"指标还能抵消团队在规划文档和愿景中过度关注"如何做"的倾向。例如，亚马逊用无人机送货到家的项目，可能有一个指标是"最小化从下单到送达的时间"，另一个指标是"最小化每单配送成本"。如果团队中有人提出替代"如何做"的方案，能在这些指标上超越无人机配送——比如家庭 3D 打印？瞬间传送？——那么指标将胜过无人机配送的愿景，新的"如何做"就可以被采纳。

### 面试与招聘

在向团队传达愿景和指标的同时，将"如何做"和部分"什么"的决策权交给团队，这将在很大程度上帮助你在组织内培养积极主动的成员。但现实是，你无法让积极主动的成员在整个职业生涯中都留在同一个团队。人们需要成长和学习，这意味着他们通常会在某个团队和特定技术栈上工作一段时间，然后转向其他团队。这是健康的，应尽可能鼓励。为了在人员流动时保持团队的新鲜血液，团队需要从外部招聘新的积极主动成员。招聘新成员分为三个阶段——首先吸引，然后筛选，最后面试。



#### 吸引有自驱力的人才

为了吸引有自驱力的人才，你需要能够以恰当的方式向团队以外的人讲述你的故事，从而吸引那些愿意为你的项目投入工作的人。通常，你会通过职位描述来传达你的故事。在撰写职位描述时，非常重要的一点是，不仅要传达团队试图实现的愿景，还要极其诚实地说明你对加入团队的个人有何期望。最糟糕的情况莫过于，你撰写了一份旨在吸引候选人，但实际工作内容却与描述不符的职位描述。有时，数据工程团队会倾向于“过度强调”岗位中的机器学习部分，而“弱化”工程部分。更糟糕的是，我们偶尔会看到有人将机器学习机会作为诱饵，吸引候选人应聘那些实际上 95%都是传统工程工作的岗位。一个基于虚假职位描述而被吸引来的候选人，绝不会是一个有自驱力的人。

同样重要的是，要仔细斟酌职位描述中使用的语言，确保其具有包容性，并能吸引最广泛的候选人群体。在撰写职位描述时，有很多潜在的陷阱可能会吓跑候选人。以下是一些建议：

*   避免列出冗长的、期望候选人掌握的技术清单。一个优秀的候选人，如果熟悉某个特定的机器学习工具包，就能很快掌握另一个。相反，应侧重于你确信在问题领域会用到的更广泛的机器学习技术——使用诸如 NLP 或 RNN 这类更宽泛的术语，而不是 TensorFlow 或 PyTorch。

*   简要说明你正在使用的敏捷流程和方法。候选人喜欢听到这样的细节：“你将与一个由其他五名工程师组成的团队一起工作，遵循敏捷原则，以两周为规划周期推进问题解决。我们相信每个人都应参与塑造我们的方向并规划我们的工作。”

在职位描述中也很容易引入性别偏见。美国国家妇女与信息技术中心（ncwit.org）提供了七条有用的建议，用于撰写能吸引最广泛候选人的职位描述：

1.  避免使用最高级或极端修饰词，例如“摇滚明星”或“世界级”之类的短语。可以尝试使用“真正创新”或“致力于创造性解决问题”。

2.  避免使用特定性别的代词（他或她）。

3.  确保所有“必需”的资格条件确实是必需的，并尽可能多地建立灵活性。

4.  在职位描述的开头，包含一个简短但引人入胜的工作概述。

5.  避免使用冗长的职责或资格条件列表。

6.  确保所有图片和图形都包含多样化的人群。

7.  检查职位描述中是否存在与“男性化/女性化”相关语言的微妙偏见。

更多示例，请参见 [`www.ncwit.org/jobdescriptionchecklist`](http://www.ncwit.org/jobdescriptionchecklist) 。

#### 筛选

现在，人们开始申请你的职位，你将收到简历和申请。在这个阶段，同样重要的是，不要让你的偏见妨碍你筛选出优秀的候选人。我们很容易在浏览一堆简历时，偏向于那些与你有相似背景的候选人。与其立刻关注候选人就读的学校或上一家工作的公司，不如看看他们参与过的项目，并思考这些项目如何能为你要招聘的职位做好准备，甚至带来新的视角。

在这个阶段，开始与候选人进行面对面交谈也很重要——我们通常喜欢通过 Skype 进行 50 分钟的面试，在面试中，我们可以要求候选人解决某种技术问题，这有助于我们了解候选人如何思考并解决难题。这个问题越接近你正在处理的实际问题越好。尝试在这次电话面试中让候选人编写实际代码。不要对候选人使用的编程语言抱有执念。候选人应该能够使用他们最熟悉的语言编写代码，而作为面试官，这也是一个机会，让你可以重温一下其他你不太喜欢的编程语言的技能。总的来说，我们不赞成将伪代码作为面试的“唯一语言”——伪代码可以作为候选人开始解释他们将使用的算法的好起点，但我们认为，看到候选人能否用他们最喜欢的编程语言清晰地表达自己的想法也很重要。

### 面试中的结对编程

我们在电话面试中使用过的一个成功技巧是结对编程方法。作为面试官，你可以在一个共享的编码窗口中编写一个单元测试（关于如何提供共享窗口的一些想法见下文）。然后，面试者可以“接管键盘”，编写代码使单元测试通过。接着，面试者可以编写下一个所需的单元测试，以解决问题的下一阶段。然后，你可以编写代码使面试者的单元测试通过——如此循环。Skype 提供了一个很好的共享编码窗口，可以通过浏览器在此处共享：[`www.skype.com/en/interviews/`](http://www.skype.com/en/interviews/) 。我们也曾打开一个 Visual Studio Code 实例，并在面试中使用屏幕共享来共享 IDE。Visual Studio 还有一个名为“Live Share”的功能，可以轻松实现这一点。



#### 面试

理想情况下，你还有最后一次机会，让其他团队成员对候选人进行补充面试。最理想的情况是，在最多一天的时间内，多位员工现场面试候选人，以判断他们是否能成为团队中的得力成员。判断一位候选人会成为团队中积极进取、充满干劲的成员，还是会成为消极怠工、缺乏动力的成员，是一项极具挑战性的任务。如果你回顾一下与现有团队共事的经历，你会发现，有些你最初认为水平不达标的人，最终却成为了坚实的贡献者。反之，你也可能遇到过在面试中表现惊艳，但实际工作中却“毒性”十足的人。那么，如何在一天之内完美地判断你的候选人处于这个光谱的哪个位置呢？事实是，你做不到，所以你需要对整个流程抱持一种更超然的心态。^(¹¹)

首先，将面试过程视为一个分类器。你需要在面试中设定高精度的阈值。这可能意味着你会拒绝一些本可以很优秀的候选人——但别太在意。但要非常小心，确保你的分类器用于评估匹配度的“特征”被无情地修剪掉那些反映你自身偏见的特征。拒绝任何基于相似度得分的特征——例如，这个人长得像我、想法像我、和我上同一所学校，或者和我喜欢同样的东西。

其次，请记住，除了非常小的团队，招聘是一个流动的、持续的过程。如果在所有阶段，团队的目标和期望都清晰明确，你就可以随着时间的推移优化团队。换句话说，你是在经营一项业务，所以你可以鼓励那些“误报”（即被错误拒绝的候选人）去其他岗位寻找机会。

言归正传，让我们探讨一下在面试中应该关注什么。我们通常从*能力*（已经具备的技能）和*潜力*（候选人可以发展的、团队所需的技能）这两个方面来考量。前者可以通过直接提问来确定，而后者则需要面试官具备更多的迂回技巧。能力和潜力涵盖了候选人当前和未来的技能；它们也体现了对团队整体工具箱的补充，以及候选人是否会放大、补充团队能力，或两者兼而有之。

我们收到过最好的职业建议是追随你的热情——工作自然会水到渠成。充满热情的人往往会自我选择与团队匹配，因为如果他们的工作与热情不符，他们会寻找其他机会。考虑到这一点，我们发现在面试过程的早期阶段，了解候选人的热情所在非常有用。虽然这看起来是一件很简单的事情——只需问“你对什么充满热情？”——但我们发现，即使不是大多数，也有很多候选人认为自己实际上对任何事情都没有热情。别信他们。虽然许多人不会给出一个高度明确的热情定义（比如“我想构建终极人工智能”），但很多人都有隐藏的热情，这些热情会体现在非应用领域。例如，我们面试并共事过的人中，有对工程实践充满热情的，有对服务架构充满热情的，有对团队和协作充满热情的，有对应用于其领域的特定新兴科学充满热情的，或者是对公司本身充满热情的。作为管理者，你的工作是发现热情并利用它为你的团队服务。作为招聘经理，你的工作是评估为你正在面试的候选人找到热情是容易还是困难。在试图引导理解其热情领域时，你必须表现得像一位优秀的电台主持人，从一位不情愿的明星那里引出故事。假设热情是存在的，而找到它所需要付出的努力，就是衡量将来利用这种热情难易程度的标尺。

在测试机器学习或数据科学能力时，我们通常喜欢采用一种递进式提问模型，将直接测试和要求从经验中举例结合起来。例如，根据我们“指标是开发核心”的观点，我们喜欢就一个简单问题的评估提问。例如：“你会如何评估一个用于判断网页是否为商业主页的分类器？”这让你和候选人可以触及以下几点：

*   分类的基础知识，包括真正例、真负例、假正例、假负例、精确率、召回率、准确率等
*   一些基础统计学知识，特别是抽样
*   处理海量数据集（如万维网）的实用方法

由此，你可以将提问线索扩展到架构细节，特别是与规模相关的方面，如果候选人具备现有能力，还可以深入到机器学习的具体细节。在考察能力时，你要看他们是否是一个真正的实践者，而不是仅仅下载了最新的开源模型并根据博客上的配方运行它的人。在考察潜力时，你要看候选人是否能识别常见的陷阱——他们是否认识到关于数据所做的假设？

在面试更高级别的职位时，我们倾向于寻找那些能在敏捷开发框架内发挥作用的特质。同样，在测试能力时，这可以通过直接提问来完成。事实上，敏捷宣言的原则提供了许多不错的讨论方向：你是如何处理需求变更的？在项目开发过程中，你是如何与客户合作的？你在哪些方面投入了技术卓越性来支持项目？是什么激励着你？

### 积极进取者的职业管理

一旦一个组织成功培养出积极进取的员工，并从外部招募到新的积极进取者，下一步就是留住并培养这些积极进取的员工。你该怎么做？



#### 心树星椅

一个重要的第一步是，将定期讨论个人在工作和职业中的追求作为优先事项。进行此类对话的一种方式是芭芭拉·格兰特为微软员工管理者开发的模型，称为“心树星椅”。

与员工对话的“心”部分，重点在于讨论他们热爱当前工作的哪些方面，以及总体上他们喜欢做什么。你可以提出以下问题：

*   你喜欢做什么？
*   目前工作中，哪部分最让你感到满足？
*   在你过往的所有工作中，你最喜欢从事哪项工作？
*   你工作中最不喜欢的事情是什么？

对话的“树”部分，是关于员工希望如何在当前职位上成长和发展。你可以提出以下问题：

*   你设想自己一年后、两年后、四年后在做什么？
*   当你观察组织中的其他人时，你希望成为组织中的谁？
*   你接下来想学习什么？
*   你接下来想发展或提升哪些技能？
*   你计划如何在接下来的一年中挑战自己？

最后，对话的“星”部分包括关于员工认为工作中什么最有价值的问题。你应该明确表示，假设每个人都希望自己的工作得到公平的报酬——这当然是“星”对话的一部分，如果有人觉得自己的经济回报不足，你应该优先处理这个问题。但理解激励员工的其他方面也同样重要。对一些人来说，他们可能受到认可的激励；另一些人则可能因承担组织中最困难的问题而受到激励；还有一些人可能因能够影响最多人而受到激励；另一些人则可能因能与他们认为最能学到东西的人共事而受到激励。你可以提出以下问题：

*   是什么让你觉得继续从事这份工作是值得的？
*   除了金钱报酬，在这里工作最有价值的是什么？

你可以选择性地为这个讨论添加第四个元素，称为“椅”。“椅”的问题是为了确定是什么让他们留在当前职位，以及什么会导致他们离开。你可以在这里提出以下问题：

*   你为什么仍然留在当前职位？
*   什么最可能导致你决定离开当前职位？
*   当你考虑下一个职位时，它会是什么？
*   你长期的理想职位是什么？

### 换椅子可能是好事

请记住，某人更换他们的“椅子”不一定是坏事。通常，一个人成长和进步最快的方式是去做不同的事情，即使他们非常擅长当前的工作。我们有过许多经历，一个项目似乎完全依赖于某个人在某个特定角色上，结果却发现当那个人离开后，新人能够更好地填补这个角色——或者至少以一种不同的方式，最终使组织变得更强大。

#### 从个人贡献者到技术负责人/架构师/管理者

大多数理性的人期望在职业目标上取得一定的、可衡量的进展。老板和员工之间明确彼此对职业目标以及实现这些目标的时间框架的期望是件好事。首先了解员工走的是哪条路径是很好的。员工未来是想成为管理者，还是想走“IC”路径？——这是微软的说法，指没有管理职责的个人贡献者。

最常见的职业路径如下：

*   **初级到专家级开发者**：这条路径适合那些希望在职业生涯中始终亲力亲为从事开发的人。走这条路径的人会随着时间的推移承担越来越有挑战性的项目。他们可能会选择在某个特定领域变得非常深入，这很有价值——有些开发者整个职业生涯都在一个特定领域和类似的应用集上工作——而另一些人则选择在多个领域广泛了解各种技术。这两种类型的开发者——专家型专才和专家型通才——对团队都很有价值。走这条路径的人需要被分配能够持续增长和拓展其技术能力的任务。

*   **技术领导力路径**：这条路径适合那些天生在技术上负责，但不一定想管理人的人。走这条路径的人擅长沟通和完善技术想法，并自然地为他们参与的项目提供技术领导。这条路径最终可以发展为团队架构师，为越来越大的项目提供技术方向。走这条路径的人需要有机会领导项目，最初是小项目和小团队，但随着时间的推移，要扩展到更大的项目和更大的团队。走这条路径的人需要学会通过影响力而非权威来领导。

*   **人员管理路径**：这条路径适合那些希望培养和发展高绩效团队，并积极影响和改变他人职业与生活的人。走这条路径的人应该对为有动力的个人创造蓬勃发展的环境充满热情。他们应该有机会承担人员管理职责，并领导组织变革计划，以成长为这些角色。

*   **专业转换路径**：偶尔你会看到有人想在团队中转换专业。例如，我们见过开发者转岗为项目经理、技术文档撰写人等。在数据工程团队中，一个常见的挑战是，当某个主要拥有经典计算机科学背景、很少接触机器学习的人，想要完全转向通常由拥有更多机器学习经验的人担任的数据科学角色时。我们处理这个问题的方式如下：
    *   **谨慎配对**：通常，在数据工程团队中，会有一些拥有强大机器学习背景的人，他们推动着团队中最重要的任务。通过将他们与有兴趣学习和建立相同技能组合的其他人配对，来传播他们的知识是很有用的。但同时，你也不想用太多“帮手”来压垮你强大的机器学习专家。找到一个平衡点，你可以将想学习更多机器学习知识的人分配到团队中，让他们与你的机器学习专家密切合作，同时又不至于过度拖慢这些专家的进度。
    *   **优先安排机会**：通常，团队中的每个人，从最资浅的开发者到最资深的开发者，都想更多地参与机器学习问题。但并非所有人都能参与其中。团队中通常仍然有大量“非机器学习”的工程工作需要完成。机器学习机会可以用来激励和留住想学习的人。交替安排传统的工程工作与更多的机器学习任务，这样你既能继续推进非机器学习工作，又能定期为开发者提供学习更多机器学习知识的机会。



## 为积极主动的个体创造高效环境

监控团队的工程环境至关重要，以确保你提供的环境能持续激励并赋能积极主动的个体。团队必须关注所谓的“开发者日常”。这涉及提出关于开发者一天工作的如下问题：

*   你今天浪费了多少时间？

*   修改模型、重新训练并测试它花了多长时间？

*   对某个功能进行代码修改并完成签入花了多长时间？

*   验证一项修改不会破坏现有产品需要多长时间？

*   构建产品需要多长时间？

*   调查并修复产品中的缺陷需要多长时间？

### 内循环与外循环

如你所见，这些问题大多关乎开发者的时间利用效率以及浪费了多少时间。在微软，团队会讨论“内循环”和“外循环”。内循环是指开发者在自己的机器上以某种方式修改产品并测试其修改所需的时间。外循环则是指修改在开发者自己的机器上验证通过后，实际将该修改发布到生产环境供客户使用所需的时间。团队最好能识别出在内循环和外循环中最常做的事情——例如，重新训练模型、修复功能代码中的缺陷或修改 Web 服务——并测量所需时间。然后，团队可以持续不懈地缩短完成这些任务的时间。

当你开始衡量产品的内循环和外循环时，会发现许多改进机会。以下是我们看到的一些内循环改进示例：

*   一个内循环的构建时间原本长达 20 分钟，通过重构和组件化构建进行了优化，将构建时间缩短至 2 分钟，这样每个人只需构建他们正在处理的产品部分，一年内节省了数千工时。

*   一个数据管道的内循环原本只能通过耗时数小时的服务器流程进行验证，通过提供一种新的数据管道变体进行了优化，该变体可在本地开发者机器上数分钟内完成验证。

*   一个用于部署网站更改的外循环原本需要数小时的测试，通过并行化测试（同时在多台机器上运行）提高了测试速度，从而进行了优化。

### 如何成为英雄

如果你真的想赢得团队的敬仰，那就做点事来改进内循环或外循环。在埃里克的一个团队中，持续集成系统随着时间的推移，从原本 1 小时完成一次签入验证，逐渐退化到需要超过 2 小时。当一位开发者暂停“日常工作”，决心深入调查时，他发现了一个影响所有运行测试的内存泄漏。修复后，集成系统恢复到了 1 小时。团队为此专门放了一天假来表彰他。

### 工具、监控与文档

除了持续优化团队的内循环和外循环，你还应考虑工具、监控和文档。这三项投入能进一步改善开发环境，从而保持团队的积极性。

工具：没有什么比能让开发者工作更轻松的工具更好了。你的团队会告诉你“开发者日常”中困难的部分，并常常会提出让这些部分变得更简单的工具创意。这些工具可能范围很广，从自动化重复操作的简单脚本，到需要更多时间开发的复杂工具。虽然你可能在工具上过度投入，但我们更常见的是，由于急于发布产品，好的工具被忽视了。为工具留出时间。以某种方式将其纳入你的常规开发流程。例如，你可以选择定期进行工具冲刺，或者选择让开发者轮流进入专注于工具开发的冲刺，或者像第 8 章“可持续开发”中描述的那样，每年安排固定的几周暂停常规产品节奏来构建工具。

监控：没有什么比无法找出产品在线上为何失败更糟糕的了。通常，良好的日志记录以及用于搜索和查询这些日志的优秀工具，能决定一个功能或网站故障是持续几分钟还是几小时。这将在第 7 章“监控”中进一步讨论。一个好的做法是每周召开一次关于上周产品任何故障的事后复盘会议。让了解故障的人参与进来。不要将其视为指责导致产品故障的开发者的机会。相反，应将其视为一个有用的学习机会，以找出可以采取哪些缓解措施来确保未来不再发生同类问题。同时讨论“检测时间”和“解决时间”。对于重大问题，应跟踪检测时间，以促使团队诚实地面对他们发现影响客户问题的速度。通常，通过更有效的监控可以缩短检测时间。通过更好的产品就地更新策略来修复问题，可以缩短解决时间。每周事后复盘会议的产出应该是工作项，并在后续的复盘会议中跟踪这些工作项，以确保它们得以完成。这将在第 8 章“可持续开发”中进一步讨论。

文档：团队中常常缺乏的、用于支持积极主动个体的最后一项是良好的文档。这里你应该问的一些问题包括：

*   团队是否有足够的文档，使得新员工加入后仅通过阅读这些文档就能快速上手？

*   团队中最常见的开发者任务（训练模型、更新功能、部署功能）是否以逐步操作的方式记录在某个地方，以便新员工能够完成这些任务？

*   开发者能否查看你的源代码仓库，并在关键目录中找到解释这些目录内容的相应自述文件？

在微软的开发者调查中，投资文档是最常出现的任务之一。通常，你的团队中会有积极主动、擅长写作并愿意投入文档工作的个体。在你的日程中为他们留出时间，并授权这些人编写文档。

### DocFX + Git

我们成功用于文档的一个系统是 DocFX 和 Git 的组合。DocFX 是一个系统，它可以处理 Markdown 文档，并提供良好的导航和搜索体验。它被用于驱动 docs.microsoft.com。当与 Git 结合使用时，你可以保留对文档所做修改的变更历史，并利用 Git 的全部功能来管理和维护文档。有关 DocFX 的更多信息，请参阅[`http://dotnet.github.io/docfx`](http://dotnet.github.io/docfx)。



### 开发者净满意度（NSAT）

我们已经提出了几个量化指标来衡量你的开发环境的生产力：

*   内循环中常见开发任务的“内循环”时间是多少
*   外循环中常见开发任务的“外循环”时间是多少
*   检测产品中问题的时间是多少
*   解决产品中问题的时间是多少

除了这些量化指标，收集一个定性指标也很有用。我们在微软使用过的一个特别有用的跟踪指标被称为开发者 NSAT（净用户满意度）。跟踪你团队的开发者 NSAT 非常容易。定期（我们每月做一次）向你团队中的每个人提出这个问题：

> *你对我们在团队中的整体开发者体验和生产力有多满意？*

1.  *非常不满意*
2.  *不满意*
3.  *既不满意也不满意*
4.  *满意*
5.  *非常满意*

你还应该问一个额外的“填空”问题：

> *哪项投入或改变能最直接地提升你的整体开发者体验和生产力？*

以匿名调查的方式提出这两个问题，并确保团队知道这是匿名的。这将鼓励诚实的回答。然后，根据该调查，你可以通过以下公式计算 NSAT 分数：

NSAT = 100 + 非常满意的百分比 – (非常不满意的百分比 + 不满意的百分比)

因此，如果你的调查得到以下结果：

*   *非常不满意：10% 的受访者*
*   *不满意：18% 的受访者*
*   *既不满意也不满意：31% 的受访者*
*   *满意：40% 的受访者*
*   *非常满意：1% 的受访者*

你的 NSAT 分数将是：

NSAT = 100 + 1 – (10 + 18) = 73

定期跟踪 NSAT，并确保它呈上升趋势而非下降趋势。投入资源到调查中“填空”部分所建议的工作上，以保持你团队的 NSAT 持续上升。

## 支持组织外部的积极个体

团队有时会忽略的一个领域是思考如何激励在团队之外甚至公司之外工作的个体。有几种主要方式可以利用这些外部个体。它们包括与开源社区互动、发表论文，以及为你的项目提供可扩展性方案，以便积极个体能够在此基础上进行构建和扩展。

开源：利用开源并为其做出贡献，是激励公司外部人员以及激励团队内部成员的好方法。开发者通常对为开源项目做出贡献感觉良好，因为其影响可能比内部项目更持久。它也能影响到比仅为一个小项目编写代码更多的人。在可能的情况下，寻找为开源项目做贡献的方法。此外，通过使用开源项目，你可以受益于公司外部那些持续改进你所使用的开源项目的积极个体。

发表论文：发表并传播你的团队在机器学习领域进行创新的方向。尽可能参加机器学习会议，并与你团队关注领域重叠的研究人员建立关系。保持参与机器学习社区对你的团队非常有激励作用，同时也为你提供了机会，去利用组织外部那些正在机器学习领域取得下一个突破的积极个体。通常，你想在团队中解决的问题，可能已经有多个已发表的论文可以参考，以获得解决思路。查阅文献，利用你问题领域中已有的研究成果。及时了解影响你感兴趣领域的最新出版物。

可扩展性：激励团队和公司外部个体的最后一种方式，是为你的产品提供一个优秀的第三方可扩展性模型。这可能简单到提供一个 REST API，允许其他方调用你产品的关键子系统，并在他们的应用程序中利用你的成果。思考一下你在产品中想解决但受限于开发资源和时间而无法解决的所有问题。然后考虑你是否可以公开一些 API，让第三方能够利用你的产品来解决这些问题。
