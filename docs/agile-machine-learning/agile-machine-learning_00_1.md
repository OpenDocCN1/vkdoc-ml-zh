# 引言

这本书源于一次偶然的相遇。2012 年 7 月，埃里克·卡特在德国完成了一项为期三年的任务——为微软将购物搜索产品推向欧洲市场——后刚刚返回美国。他感到非常失望，因为他在欧洲领导的努力正在终止，于是开始寻找新的工作。在探索微软搜索引擎必应（Bing）的机会时，他遇到了马修·赫斯特。马修作为 Live Labs 的成员加入了微软，Live Labs 是一个创新小组，负责探索围绕搜索、云和互联技术的新颖解决方案和应用。从那时起，他参与了地图和本地搜索的各种迭代版本，通常致力于将文本与位置连接起来的功能。随后，他们形成了一种互补的合作关系，极大地提升了必应本地搜索的质量，并最终引领两人踏上了一段学习之旅，了解数据工程项目如何从应用*敏捷原则*中受益。

敏捷宣言（或全称*敏捷软件开发宣言*）于 2001 年由十七位签署人合作诞生^(¹)。它被概括为四个价值观（重视*个体与互动*胜过流程与工具，重视*可工作的软件*胜过详尽的文档，重视*客户合作*胜过合同谈判，重视*响应变化*胜过遵循计划）和十二条原则。在本书中，我们逐一审视每条原则，并将其与我们在多个项目和情境中处理数据和推理方法的经验联系起来。

当两位作者相遇时，必应的本地搜索产品还远未成熟。本地企业目录的质量正在提升，但仍远落后于当时的市场领导者谷歌。马修在本地搜索数据团队工作，他和团队其他成员一直在探索一些创新想法，以更好地利用网络并整合机器学习，从而大幅改进目录。埃里克看到了必应本地搜索领域中存在的许多引人注目的挑战，并决定加入，担任必应本地数据团队的工程经理。

在职业生涯的这个阶段，埃里克对在微软管理团队并不陌生，他曾参与多个 Visual Studio 相关产品以及现已解散的“购物搜索”项目。然而，正是在与 Visual Studio 合作期间，他发现了敏捷的内在价值，以及团队在遵循敏捷原则时效率更高、更快乐。他希望能将这一点带入新团队，却发现自己陷入了困境——如何将敏捷应用于一个更侧重于产出数据而非产出软件的团队？将敏捷引入数据工程团队需要什么？

这并不容易。起初，敏捷就像一个入侵的外来因素。团队文化崇尚通过实验发现宏大构想、进行长期研究以及开展大量试错式的科学项目——这些似乎都与 Scrum、迭代开发、可预测性、简洁性以及频繁交付可工作软件等敏捷原则背道而驰。对于一个专注于构建包含全球所有企业的极其精确数据库的团队来说，定义“完成”几乎是不可能的。毕竟，数据中唯一不变的就是它包含错误——这项工作实际上永无止境。面对诸如向利益相关者沟通团队如何以及在何处取得进展、判断某项特定开发投资是否值得、以及确保以规律且可持续的节奏交付改进等挑战，采用现代敏捷方法显然至关重要。但如何在一个由数据科学家和传统工程师组成、且都致力于数据导向交付物的团队中应用敏捷呢？

传统的敏捷流程旨在减少不确定性并回答诸如“客户想要什么”以及“如何可靠且持续地交付软件”等问题。但在这个新项目、新世界中，我们已经知道客户想要什么（一个完美的本地企业目录^(²)），但我们还需要回答诸如“数据里有什么？”以及“基于这些数据，我们能交付什么？”等问题。我们需要敏捷方法，但要针对一个现代的、混合人才的、数据工程团队进行修订。

当我们应对“下一代”机器学习挑战时，我们毫无疑问地发现，敏捷原则可以用来解决问题并减少关于数据的不确定性，从而使团队更快乐、更高效。

我们整合这套现代化敏捷方法论的希望在于，本书中经过验证的指导和来之不易的见解，能够帮助个人、技术负责人和管理者在当今机器学习和大数据领域激动人心的工作中提高生产力。

2019 年 6 月

埃里克·卡特

马修·赫斯特
