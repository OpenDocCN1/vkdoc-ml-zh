# 23. 智能编排环境

本章讨论了一些有助于成功实现智能编排的常见活动。这些示例展示了如何充分利用智能系统，包括以下内容：

*   **监控成功标准**：了解系统是否在实现其目标，以及其表现是变好还是变差。
*   **检查交互过程**：像用户一样体验上下文，并查看用户所获得的结果。
*   **平衡体验**：使体验的力度更强或更弱，可能改变交互类型，或调整交互的显著性和频率。
*   **覆盖智能决策**：纠正偶发的严重错误，或帮助优化常见上下文。
*   **创建新智能**：管理智能并生成新模型，以应对问题、用户或数据范围变化时出现的新问题。

智能系统可以从所有这些活动以及更多活动中受益。其中一些活动可以作为实现的一部分来构建——例如，一个显示总体目标进展的指标仪表板。另一些活动则可以以更临时的方式处理——例如，查询原始遥测数据源，以拼凑出导致问题的交互过程。

本章将依次讨论编排活动，并提供一些关于如何（如果你选择这样做的话）在每个领域进行投入的想法，以及决定投入多少的一些标准。

## 监控成功标准

你必须能够判断系统是否在实现其目标。这涉及获取遥测数据，纠正任何采样和中断问题，并生成所有参与者都能理解的答案——可能是一些数字，也可能是一张图表。回想一下，这可能涉及以下任何一项：

*   **业务目标和领先指标**，特别是展示重度使用系统智能部分的用户与不使用该部分的用户之间的差异。
*   **用户成果**，表明智能系统在帮助用户实现你期望的成果方面的有效性。
*   **模型属性**，表明智能判断正确或错误的频率（无论用户最终取得了什么成果）。

监控成功标准至关重要。每个功能正常的智能系统都必须有人每天了解其运行状况，并关心它是否在实现其目标。

监控成功标准的投入级别包括：

*   **临时性**：少数人具备衡量系统目标并生成答案的技能，可能通过交叉检查当前的遥测设置、调整脚本、运行脚本、将结果复制到演示形式（如图表）并进行分发。
*   **基于工具**：团队中的任何人都可以运行一个工具，该工具创建并执行正确的查询，然后以合适的演示格式输出答案。
*   **自动化**：系统定期自动运行查询，并将结果存档在所有参与者都能找到的地方。
*   **基于警报**：系统不仅自动化指标，还对其进行监控，并在发生某些情况时向参与者发出警报，包括：
    *   **重大退化**：指标远低于上次测量值。例如，自昨天以来错误数量增加了 10%。
    *   **显著、持续的侵蚀**：指标逐渐下降的时间足够长，以至于超过了某个阈值。例如，在过去一个月中，获得良好结果的用户比例下降了 10%。
*   **群体追踪**：系统追踪重要子群体以及整体群体的指标。这可能包括来自特定地点、具有特定使用模式、特定人口统计特征等的用户。

投入监控成功标准的判断标准：

*   几乎每个智能系统都应该为成功标准以及促成成功标准的关键因素实施基于警报的监控。

## 检查交互过程

检查交互过程涉及收集与特定用户交互相关的所有遥测数据，并能够端到端地查看该交互过程。这包括用户交互时的上下文、正在运行的智能版本、智能给出的答案、由此智能答案产生的体验、用户如何与该体验进行交互，以及用户最终获得了什么结果。

这对于调试问题、追踪错误、了解用户如何看待智能系统，以及获得关于用户体验选项的直觉至关重要。

检查交互过程的投入级别包括：

*   **临时性**：少数人具备找到交互过程所有部分并理解它们之间关系的技能。他们可能需要进行一些侦探工作来识别特定的交互（或具有特定属性的交互），并且基于采样，可能能找到也可能找不到任何特定的交互。
*   **基于工具**：团队中的任何人都可以识别一个交互（可能通过用户和时间），并查看相关的遥测数据。该工具还可以支持查询特定类型的交互（例如，智能给出了特定答案而用户获得了特定结果的情况），并检查其中的样本。
*   **基于浏览器**：团队中的任何人都可以像使用工具一样找到交互，然后像用户一样体验该交互过程，看到用户看到的体验、他们点击的按钮、他们获得的结果等等。
*   **从用户获取数据**：编排者有机会标记特定类型的交互，并向用户询问有关其体验的问题。例如，可以通过指定一些上下文，然后对遇到该上下文的一小部分用户进行调查来实现。这些调查可能会要求用户评价他们的体验，回答一两个问题，或表明他们获得了好的还是坏的结果。

投入检查交互过程的判断标准：

*   如果你需要广泛的人员能够理解交互过程。例如，让体验创建者和业务利益相关者了解用户是如何体验智能系统的。
*   如果你需要建立支持能力来帮助处理错误。工具可以让非实现专家的普通人参与进来。
*   如果你的系统存在高成本错误，并且你预计编排的主要部分将涉及定期缓解，那么你将需要投入检查交互过程。



## 平衡体验

随着问题、用户群体和智能的变化，会带来优化体验的机会。例如，当智能是全新的且质量较差时，体验可能会非常被动。也许它不会频繁出现，也许它以用户容易忽略的方式呈现。但随着时间的推移，智能会变得更好，用户可能会通过更具强制性的体验获得更积极的结果。

用于平衡体验的投入层级包括：

*   **临时方案**：通过修改代码并重新部署软件来改变体验。
*   **参数更新**：编排者可以更改影响体验的参数，并以相对较低的成本（例如在智能更新时）推送这些参数。参数可能包括：
    *   交互频率。
    *   提示的颜色或大小。
    *   体验中使用的文本。
    *   自动化操作的阈值。
    *   等等。
*   **体验备选方案**：创建多种体验，编排者能够（使用类似于参数的方式）在它们之间切换。例如，你可以创建一个带有微妙提示的体验版本、一个带有醒目提示的版本，以及一个自动化操作的版本。然后编排者可以在这些版本之间切换，以随时间推移实现目标。
*   **体验语言**：编排者可以脱离代码变更来编写和部署体验，类似于将智能与实现分离。这可以通过在客户端下载并执行的脚本中指定体验来实现。或者，它可能受到更多限制，以便非工程师也能安全地进行更改；例如，一种具有受限运行时的体验标记语言。

投入平衡体验的评判标准：

*   如果你的编排团队没有工程资源，那么你可能希望为体验创建一些非工程性的控制手段。
*   如果向客户部署新的客户端代码需要很长时间，你可能希望投入资源，通过参数和数据文件更新来控制体验。
*   如果你认为在智能系统的生命周期内会多次更改体验，你可以选择投入资源使其易于更改。
*   如果以上情况都不符合——你确实有工程资源，可以轻松部署代码，并且预计不会有太多更改——那么采用临时方案进行体验更新几乎肯定更便宜。

## 覆盖智能

覆盖智能涉及识别少数上下文，并手动编写智能应为这些上下文提供的答案。你可能希望这样做是为了纠正代价高昂（或令人尴尬）的错误。你可能希望这样做是为了优化一些常见的上下文。你可能希望这样做是为了支持某些业务目标（例如推广系统中的某个内容）。你可能不想过多地覆盖智能——但当你需要时，你会非常需要它。

用于覆盖智能的投入层级包括：

*   **临时方案**：依赖智能创建者破解学习过程以尝试实现特定结果（这非常困难），或者依赖工程师将所需的覆盖硬编码到代码中并部署给客户。
*   **作为智能源**：将覆盖视为一个非常简单的智能源，与系统的其他智能一起部署，并在运行时具有最高优先级。也许使用某种简单格式的数据文件来表示，该文件将上下文映射到结果。
*   **基于工具**：将覆盖视为一个智能源，但创建工具来支持编排者。工具应包括以下功能：
    *   确保要覆盖的上下文被正确指定。
    *   提供关于指定上下文的普遍性以及这些上下文的当前智能响应的反馈。
    *   提供关于现有覆盖的反馈，包括覆盖的数量以及它们影响的用户数量。
    *   跟踪谁在进行覆盖以及覆盖结果的好坏。
    *   管理覆盖的过期。
*   **基于浏览器**：将工具集成到一个支持套件中，包括在一个地方查找交互、查看交互和覆盖交互的方法。

投入覆盖智能的评判标准：

*   如果你的系统可能犯下代价非常高昂的错误，你几乎肯定希望投入资源进行智能覆盖，可能还需要围绕这里讨论的工具添加跟踪和工作流管理。我们将在下一章关于处理错误的内容中更详细地讨论这一点。
*   覆盖智能对于智能创建者来说也是一个非常有用的缓冲。你最不希望看到的是，智能系统中的大量参与者使用产品，发现无数小问题，并将其作为针对智能创建过程的缺陷提交。智能会犯错误。因为每个缺陷而责备创建者无济于事。拥有覆盖一些更重要问题的能力可以让每个人都感觉更好。

## 创建智能

编排的一个重要部分是控制和创建驱动智能系统的智能。本节回顾并总结了一些有助于智能成长和产生影响的投入。

创建智能的投入可能包括：

*   **智能管理**：这将包括以下内容：
    *   控制智能更新和部署的时间与方式。
    *   控制智能存在于何处。
    *   向系统添加新的智能源。
    *   控制智能如何组合。
*   **自动化机器学习实现**：这些系统定期生成新的智能，几乎不需要或完全不需要监督。这些系统可能提供控制手段来改变智能生成的方式，包括以下内容：
    *   使用多少数据。
    *   使用哪些数据。
    *   运行的频率。
    *   花费多少时间搜索好的模型。
    *   建模过程中任何其他可调参数。
*   **智能创建环境**：收集捕获上下文和结果的遥测数据，并使其可用于机器学习，包括尝试新的机器学习算法、新的特征工程以及整合新的见解。这些可以产生临时的新的智能，或找到改进现有自动化学习系统的方法。
*   **特征工程支持**：智能创建者能够非常轻松地尝试新特征，如果发现有效的特征，能够快速安全地将其部署给客户。
*   **遥测系统**：编排者可以指定要收集哪些数据以及收集多少数据。

投入创建智能的评判标准：

智能创建对于智能系统来说相当重要（名字里就写着呢）。你最终可能会投入多个系统来支持这个过程。

最有效的工具往往能够：

*   帮助防止错误。
*   自动化繁琐的任务。
*   简化多步骤流程。
*   留下一些简单的审计追踪。

在构建支持智能创建的工具时，避免试图干扰核心的智能创建工具（如机器学习系统或运行时）。这些通常是标准的，对其进行创新不太可能成为你价值主张的核心。



## 总结

本书介绍了许多对运行智能系统至关重要的工具。本章总结了一些关键工具，包括投资这些工具时需遵循的标准和方法。这些工具包括：

*   监控成功标准
*   检查交互
*   平衡体验
*   覆盖智能
*   创造智能

在实施过程中，即使不在这方面投入太多，你也可以构建一个成功的智能系统。但在系统的整个生命周期中，你很可能需要完成所有这些活动。你可以自行决定投入多少人力，以及愿意在工具上投入多少资源。

请记住，拥有良好的工具可以让你随着时间的推移，将人员配置从系统的创建者（他们通常喜欢从事令人兴奋的新事物）转变为熟练的编排者（他们需要成为追求持续卓越的通才）。这两种技能组合截然不同。

通常，编排环境会随着智能系统的发展而演变，在长期内，资金会投入到那些能带来最大价值的领域，直到进一步的投资不再有意义。
