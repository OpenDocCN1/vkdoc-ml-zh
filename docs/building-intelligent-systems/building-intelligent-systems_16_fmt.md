# 13. 智能的部署位置

在构建智能系统时，你需要决定智能的部署位置。也就是说，你将在何处将模型、运行时和上下文整合在一起以生成预测，然后如何将这些预测传回智能体验。

运行时可以位于用户设备上，在这种情况下，你需要弄清楚如何在整个用户群中更新模型。

运行时也可以位于你运行的服务中，在这种情况下，你必须弄清楚如何以足够低的成本和延迟，将上下文（或特征）从用户设备传输到服务，从而使端到端体验有效。

本章讨论如何决定智能的部署位置。首先讨论决定智能部署位置时需要考虑的因素，包括延迟和成本，以及它们为何对各种类型的智能体验至关重要。然后讨论在客户端和服务之间定位智能的常见模式，包括每种选项的优缺点。

## 定位智能的考量因素

决定智能部署位置时，一些关键的考量因素如下：

*   更新智能的延迟。
*   执行智能的延迟。
*   运行智能的成本。
*   用户离线时会发生什么。

通常，你需要在上述属性之间进行权衡。本节将逐一讨论这些因素。

### 更新延迟

决定智能部署位置时，一个考量因素是尝试更新智能时产生的延迟。新的智能在到达运行时并替换旧智能之前，无法让用户受益。

当运行时与智能创建环境位于同一台计算机上时，更新智能的延迟可能非常短；当运行时位于客户端计算机上，且该客户端计算机不经常连接互联网时（因此只能偶尔获取新智能），延迟可能会非常长。

在以下情况下，将智能传输到运行时的延迟非常重要：

*   智能的质量正在快速提升。
*   你试图解决的问题正在快速变化。
*   存在代价高昂的错误风险。

我们将更详细地讨论这些更新延迟可能导致问题的情况，包括它们如何影响智能体验的示例。

#### 质量快速提升

当智能的质量快速提升时，更新智能的延迟就变得重要。

当问题较新时，很容易取得进展。会有各种技术可供探索。每天都会有新数据到来，新用户会以你未曾预料的方式使用产品。会有兴奋感和活力。智能的质量可能会迅速提高。

例如，假设这是第一天——你刚刚发布了你的智能鞋。这款鞋旨在根据穿着者的活动调整松紧度。坐着无所事事？鞋子会自动放松，松开鞋带，让穿着者更舒适。但如果用户开始跑步？跳跃？鞋子会自动收紧鞋带，让穿着者获得更好的支撑，减少受伤的可能性。

你进行了一次盛大的发布。市场上有成千上万双智能鞋。你正在获取遥测数据，了解用户如何移动，何时覆盖鞋子设置以收紧鞋带，以及何时覆盖设置以放松鞋带。你会想利用所有这些数据来生成新的智能。

如果你生成了新的智能，进行了测试，并确定它并不比你发布时的智能好多少——那没问题！无需担心更新智能的延迟，因为你没有任何收益。

但如果新的智能更好——好得多——你会急于将其推送到市场上所有的鞋子上。因为用户正穿着这些鞋子。他们会与朋友交谈。评论家会撰写文章。你会想快速更新那个智能！

当智能快速改进时，部署延迟会阻碍你利用这些智能。这在问题规模非常大（包含非常多的上下文）或问题非常难以解决（质量将在很长一段时间内持续改进）的情况下尤其重要。

#### 问题快速变化

当问题快速变化时，更新智能的延迟就变得重要，因为问题可能是开放式的或随时间变化的。

在某些领域，新上下文出现缓慢，需要数周或数月的时间。例如，修建新道路需要时间；音乐品味演变缓慢；新的烤面包机产品并非每天上市。在这些情况下，部署新智能有几天或几周的延迟可能无关紧要。

另一方面，在某些领域，新上下文出现迅速，每天成百上千次。例如，每秒都有新的垃圾邮件攻击发生；每天有数百篇新新闻文章被撰写；飓风登陆；股市崩盘。在这些情况下，能够快速部署新智能可能至关重要。

问题变化有两个重要方面：

1.  新上下文出现的速度有多快？
2.  现有上下文消失的速度有多快？

在那些新上下文不断添加，但旧上下文在相当长的时间内仍然相关的领域，侵蚀会缓慢发生。例如，当一条新道路建成时，你的智能可能不知道如何处理它，但你的智能在它已知的所有现有道路上仍然可以正常工作。

在那些新上下文取代旧上下文，且你昨天的智能今天不再有用的领域，侵蚀会迅速发生。例如，当一首新歌登上排行榜榜首时，一首老歌就会退出。当垃圾邮件发送者开始新的攻击时，他们会停止旧的攻击。

当一个问题频繁变化，以至于侵蚀了现有智能的质量时，更新智能的延迟可能成为智能系统成功的关键因素。

#### 代价高昂的错误风险

当智能系统可能犯下需要快速纠正的代价高昂的错误时，更新智能的延迟就变得至关重要。

智能系统会犯各种错误。有些错误并不太严重，尤其是当智能体验能帮助用户应对这些错误时。但有些错误则可能成为真正的问题。

以智能鞋为例，鞋带会根据穿着者的动作自动放松或收紧。想象一下，有极小一部分用户会以某种特定方式坐立不安，导致鞋子紧紧夹住他们的脚，带来疼痛。

或者想象一下，有一小部分用户在棒球队中担任右外野手。他们百分之九十九的时间都站在那里，看着云彩飘过——而百分之一的时间则需要疯狂冲刺去接一个高飞球。也许智能鞋跟不上这种节奏。也许右外野手会因此跑掉鞋子、滑倒并受伤。

当你的智能系统所犯的错误代价高昂，并且这些代价无法通过良好的用户体验来减轻时，延迟就会变得非常痛苦。想象一下，用户日复一日地打电话、投诉、哭诉你给他们造成的损害，而你却在等待新的智能进行传播。这会让你感觉糟糕，也可能让你的业务面临风险。

### 执行延迟

决定智能应置于何处的另一个考量因素是运行时执行智能的延迟。

要执行智能，系统必须收集上下文，将上下文转换为特征，将特征传输到智能所在的位置（有时是整个上下文被传输，特征提取稍后进行），等待智能执行，等待智能执行结果返回给体验层，然后更新体验。这些步骤中的每一步都可能引入执行智能的延迟。

当智能运行时与智能体验位于同一台计算机上时，执行延迟可能很短；当智能运行时与智能体验位于不同的计算机上时，延迟则可能很长。

在以下情况下，智能执行延迟可能成为问题：

*   用户必须等待延迟。
*   正确答案变化迅速且剧烈。

延迟及其对用户的影响可能难以预测。有时用户并不在意一点点延迟。有时一点点延迟就会让他们抓狂，彻底毁掉一种体验。尝试设计那些延迟权衡可以（在编排过程中）轻松更改的体验，以便能够用真实用户测试各种选项。

#### 智能体验中的延迟

当用户注意到执行延迟时，尤其是当他们必须等待延迟才能继续操作时，延迟就变得重要。这可能发生在以下情况：

*   智能调用是渲染体验的重要组成部分。想象一个应用程序在正确渲染之前需要多次智能调用。也许应用程序需要在渲染内容之前判断该内容对用户是否有潜在危害或冒犯性。如果用户在等待智能调用期间无事可做，那么智能执行延迟就可能成为问题。
*   智能调用是交互式的。想象一个用户直接与智能进行交互的应用程序。也许他们拨动一个开关，期望灯能瞬间亮起。如果开关在改变灯光状态前需要与智能系统确认，而这次智能调用需要几百或几千毫秒——用户可能会撞到脚趾。

另一方面，本质上是异步的智能体验，例如决定是否向用户显示提示，对执行延迟则不那么敏感。

#### 正确答案发生剧烈变化

当正确答案变化迅速且剧烈时，执行智能的延迟就变得至关重要。

想象一下创建一个用于操控无人机的智能系统。无人机正飞向一个目标；正确的答案是径直飞向目标。没问题。然后有人走到了无人机前面。或者想象无人机在一个美丽、湛蓝、阳光明媚的日子里飞行，突然一阵狂风不知从何处刮来。在这些情况下，无人机的正确控制指令发生了变化，而且变化得非常快。

当智能系统的正确行动方案变化迅速且剧烈时，执行智能的延迟可能导致严重故障。

### 运营成本

决定智能应置于何处的另一个考量因素是智能系统的运营成本。

分发和执行智能需要消耗 CPU、RAM 和网络带宽。这些都需要花钱。一些可能推高智能系统成本的关键因素包括：

*   分发智能的成本。
*   执行智能的成本。

#### 分发智能的成本

分发智能通常以带宽费用的形式，既让服务方也让用户方花钱。每一份新的智能都需要托管（例如在 Web 服务上），并且运行时必须定期检查新智能，然后下载找到的任何智能。此成本与智能必须到达的运行时数量（托管它的客户端或服务的数量）、智能更新的大小以及更新频率成正比。对于互联网规模的智能系统，分发智能的成本可能非常巨大。

考虑用户的成本也很重要。如果主要使用场景是宽带用户，分发模型可能不是问题——对他们来说成本可能不高。但当用户使用移动设备，或者处于网络使用被更仔细计量和收费的地区时，用于智能分发的带宽就可能成为一个重要的考量因素。

#### 执行智能的成本

当智能位于服务端，而客户端必须将上下文（或特征）发送到服务端并等待响应时，执行智能也会产生带宽成本。根据上下文的大小和调用的频率，将上下文发送到服务端的成本可能高于将智能发送到客户端的成本。请记住，遥测和监控也需要从客户端收集一些上下文和特征信息；有机会将工作合并以降低成本。

执行智能还会消耗 CPU 周期和 RAM。将智能运行时放在客户端的好处是用户承担这些成本。但某些类型的智能执行起来可能非常昂贵，而某些客户端（如移动设备）存在资源限制，使得重量级的智能运行时变得不切实际。在这些情况下，在服务端使用智能运行时（可能配备定制硬件，如 GPU 或 FPGA）可以实现更高效的智能。

在考虑运营成本时，应力求实现以下目标：

1.  对用户敏感，不要求他们承担对他们来说重要的成本（包括带宽，还有移动设备的电量等）。
2.  让用户承担他们不会注意到的部分成本（这样你就不必购买大量服务器）。

平衡运行智能系统的所有成本，并随着用户数量和情报质量的增长而良好地扩展。

### 离线运行

在决定智能应部署在何处时，另一个需要考虑的因素是：智能系统是否需要在离线（且无法联系任何服务）状态下运行。

并非所有智能系统都需要在离线时工作。例如，交通预测系统无需在用户乘坐飞机飞越太平洋时工作。但有时智能系统确实需要离线运行——例如，当智能运行在受限环境（如军用车辆）或生命攸关的系统中时。

当离线运行至关重要时，智能的某个版本必须驻留在客户端。这可以是完整的智能系统，也可以更像是一个备份——整体智能的精简版本，用于在服务恢复在线期间维持用户的基本使用。

## 智能的部署位置

本节将更详细地探讨智能部署的一些选项。它介绍了一些常见模式，包括：

*   产品中的静态智能
*   客户端智能
*   以服务器为中心的智能
*   后端（缓存）智能
*   混合智能

本节将讨论每种方法，并探讨它们在应对智能部署位置的四个考量因素方面的表现：`更新延迟`、`执行延迟`、`运营成本`以及`离线运行`。

### 产品中的静态智能

无需借助任何智能系统组件，也可以实现智能。只需收集一批训练数据，生成一个模型，将其与软件捆绑在一起，然后发布即可。

这与发布传统程序非常相似。你构建它，尽你所能进行测试——在实验室里，或者通过焦点小组和 Beta 测试与客户一起——不断调整直到满意，然后将其发布到世界。

这种方法的优点是系统工程成本更低。对于许多问题来说，它可能已经足够好了。它可以在无法建立用户与智能创建之间闭环的情况下工作。并且仍然存在获取反馈（通过评论和客户支持电话）以及通过传统软件更新来更新智能的可能性。

缺点是智能更新将更加困难，使得这种方法不太适合开放式、随时间变化或困难的问题。

*   `更新智能的延迟`：差
*   `执行延迟`：极好
*   `运营成本`：低廉
*   `离线运行`：是

缺点总结：难以更新智能。存在无法衡量的智能错误风险。没有数据可用于改进智能。

### 客户端智能

客户端智能完全在客户端上执行。也就是说，智能运行时完全驻留在客户端，客户端会定期下载新的智能。

下载内容通常包括新模型、解释模型输出的新阈值（如果智能封装在 API 中——理应如此），以及（有时）新的特征提取代码。

客户端智能通常允许将相对更多的资源用于执行智能。原因之一是智能可以以相对较低的成本消耗客户端的空闲资源（移动设备上可能除了电量消耗外）。另一个原因是运行时延迟不会增加任何服务调用的延迟，因此在影响用户体验（用户可感知的层面）之前，有相对更多的时间进行处理。

客户端智能的主要挑战在于决定何时以及如何向客户端推送新的智能。例如，如果智能大小为 10 兆字节，并且有十万个客户端，那么每次智能更新大约需要消耗 1TB 的带宽。此外，模型通常不易压缩，也不适合增量更新，因此通常需要全额支付这笔成本。

客户端智能的另一个潜在复杂性是处理不同版本的智能。一些用户会处于离线状态，无法收到你希望发送的每一次智能更新。一些用户可能会选择退出更新（可能通过防火墙），因为他们不喜欢有东西下载到他们的机器上。这些情况将使解读用户问题变得更加困难。

客户端模型的另一个缺点是，它们将你的智能置于任何想要窥探的人手中：可能是竞争对手，可能是想滥用你的服务或用户的人——比如垃圾邮件发送者。一旦有人获得了你的模型，他们就可以对其进行测试。他们可以自动化这些测试。他们可以找出什么样的输入能让模型给出一个答案，什么样的输入能让它给出另一个答案。他们可以找到对其上下文（电子邮件、网页、产品等）的修改方式，从而诱使你的模型犯下他们想要的那种错误。

*   `更新智能的延迟`：可变
*   `执行延迟`：极好
*   `运营成本`：基于更新频率
*   `离线运行`：是

缺点总结：向客户端推送复杂智能的成本可能很高。难以让所有客户端与更新保持同步。客户端资源可能受限。将智能暴露于外界。

### 以服务器为中心的智能

以服务器为中心的智能在服务端实时运行。也就是说，客户端获取上下文（或特征）并将其发送到服务器，服务器根据这些特征执行智能，并将结果返回给客户端。

使用以服务器为中心的智能，可以通过向运行智能的服务器（或服务器集群）推送新模型，快速且可控地更新模型。这也使得遥测和监控更加容易，因为需要记录的大部分数据已经作为智能调用的一部分存在于服务中。

但是，以服务器为中心的智能需要随着用户群的扩大而进行扩展。例如，如果每秒有一百个智能请求，服务必须能够非常快速地执行智能，并且很可能是并行执行。

*   `更新智能的延迟`：好
*   `执行延迟`：可变，但包含互联网往返时间
*   `运营成本`：服务基础设施和带宽可能产生显著成本；可能消耗用户的带宽
*   `离线运行`：否

缺点总结：智能调用存在延迟。服务基础设施和带宽成本。用户带宽成本。运行能够实时执行智能的服务器的成本。

### 后端（缓存）智能

后端智能涉及离线运行智能、缓存结果，并将这些缓存结果投递到需要的地方。当分析有限数量的事物时，缓存智能非常有效，例如图书馆中的所有电子书、服务可推荐的所有歌曲，或智能洒水器销售区域的所有邮政编码。但即使事物数量无限，只要上下文变化缓慢，后端智能也同样适用。

例如，一个洒水器被销售到一个新的邮政编码区域。该服务之前从未考虑过这个邮政编码，因此它会返回一个关于最佳浇水时间的默认猜测。但随后后端启动，检查它能找到的关于该邮政编码的所有信息，以生成一个良好的浇水计划，并将此计划添加到其缓存中。下次再有洒水器在该邮政编码区域售出时，服务就知道如何精确浇水了（也许系统甚至会为那个触发整个流程的“倒霉蛋”更新浇水计划）。

与其他方案相比，后端智能系统可以在每个智能决策上投入更多的资源和时间。例如，设想一个极其复杂的浇水计划模型，它需要在一台高端服务器上运行一小时，来决定每个邮政编码区域应如何浇水。它会分析卫星图像、交通模式、该地区鸟类和青蛙的迁徙情况——无所不包。这样的模型如果放在洒水器的嵌入式计算机上运行，可能需要数月时间——这根本不现实。它也无法在需要每秒响应数百次调用的服务器上运行——绝无可能。但它可以在后端“时不时地”运行，其分析结果可以被缓存。

智能缓存可以存在于服务中；其部分内容也可以分发到客户端。

后端智能的一个缺点是，更换模型的成本可能更高，因为所有先前缓存的结果可能都需要重新计算。

另一个缺点是，它仅在能够利用智能调用的上下文来“查找”相关智能时才有效。当上下文描述的是一个实体（如一个网页、一个地点或一部电影）时，这种方法有效。但当上下文描述的是不太具体的事物时，比如用户生成的文本块、传感器阵列的一系列输出或一段视频剪辑，这种方法就失效了。

*   `智能更新延迟`：可变
*   `执行延迟`：可变
*   `运营成本`：基于使用量
*   `离线运行`：部分支持

缺点总结：当上下文快速变化，或上下文的正确答案快速变化时，效率不高。更换模型和重建智能缓存的成本可能很高。将智能限制在可被查找的事物上。

### 混合智能

在实践中，建立结合了上述几种方法的混合智能系统是非常有用的。

例如，一个系统可能使用后端智能来深度分析热门项目，而使用客户端智能来评估其他所有内容。

或者，一个系统可能在大多数情况下使用客户端智能，但当决策后果严重时，会与服务进行双重校验。

混合智能可以掩盖其各个组件的弱点。

但是，混合智能的构建和编排可能更为复杂。试想，如果系统给出了错误答案，错误来自智能的哪个部分？是客户端模型？还是缓存在服务中的智能？或者是两者之间某种微妙的交互？

有时，甚至很难确切知道在错误发生时，所有这些组件处于何种状态。

尽管如此，大多数大型智能系统在决定其智能应驻留何处时，都会采用某种形式的混合方法。

## 总结

选择智能的驻留位置是创建成功智能系统的重要一环。智能的位置会影响：

*   `更新智能的延迟`：这取决于智能从创建环境移动到运行时环境需要走多远，以及运行时环境在线接收更新的频率。
*   `执行智能的延迟`：这取决于将上下文和特征从智能体验移动到智能运行时，再将答案移回所需的时间。
*   `运营智能系统的成本`：这取决于移动智能、上下文和特征所需支付的带宽费用，以及执行智能所需支付的 CPU 费用。
*   `系统离线工作的能力`：这取决于当客户端无法与你的服务组件通信时，智能能在多大程度上在客户端运行。

平衡这些属性有多种选择。以下是一些常见模式：

*   `静态智能`：将智能完全置于客户端，完全不连接服务。
*   `客户端智能`：将智能完全置于客户端，但连接服务以进行智能更新和遥测。
*   `服务端中心智能`：将智能完全置于服务中，每次需要在某个上下文上执行智能时，都需要调用服务。
*   `后端（缓存）智能`：在常见上下文上离线执行智能，并通过缓存提供答案。
*   `混合智能`：这是大多数大规模智能系统的现实情况，它结合了多种其他方法来实现系统目标。
