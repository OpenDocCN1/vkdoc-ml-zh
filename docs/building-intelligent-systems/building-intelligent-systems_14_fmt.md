# 11. 智能实现的组成部分

为了产生影响力，智能必须与用户相连接。

也就是说，当用户与系统交互时，智能必须以正确的输入被执行，并且用户体验必须做出响应。当新的智能被创建时，它必须经过验证并部署到需要的地方。此外，还必须具备判断一切是否正常运作的方法，以及收集所需信息以持续改进智能的机制。

智能实现负责处理所有这些方面。它是创建智能服务的基础。

打个比方，考虑一个网络服务器。一个网络服务器的实现需要接受网络连接、进行身份验证、解释请求并找到正确的内容、处理内容（可能运行脚本）、提供服务、创建日志——以及更多其他功能。一旦网络服务器实现可用，内容创作者就可以利用它来制作各种有用的网站。

这与智能系统的实现类似——它允许智能编排者随着时间的推移产生有用的用户交互。智能、人工智能和机器学习正在改变世界，但只有通过恰当的智能系统实现，它们才能发挥其潜力。

本章介绍构成智能系统实现的各个组件。

## 智能实现示例

想象一个旨在帮助用户判断网页是否有趣的智能系统。用户浏览到一个页面，如果系统认为用户阅读该页面时会笑，就会弹出一个笑脸表情。这样一来，就再也不会有人错过任何有趣的内容了……

这很简单。我们来讨论一下这个智能系统可能如何实现。

首先需要一个能够检查网页内容并评估其是否有趣的程序。这很可能是一个通过机器学习产生的模型，但也可能是一些简单的启发式规则。例如，一个非常简单的启发式规则可能是：任何包含“走进酒吧”或“是谁呀”这些短语的页面都是有趣的，而不包含这些短语的页面则不是有趣的。对某些人来说，这或许是真的——也许你也有那样的叔叔……

有人可以为网络浏览器编写一个包含此模型的插件。当加载一个新网页时，该插件会获取页面内容，对照模型进行检查，并根据模型判断结果显示相应的用户体验（如果模型认为页面有趣则显示笑脸，如果认为无趣则不显示任何内容）。这个插件是一个非常简单的智能实现。

但是，发布这个插件，看到用户下载它，很快就会有人想知道它是否有效。因此，这个插件可能包含一种让用户提供反馈的方式。如果用户浏览到系统认为有趣但自己并未发笑的页面底部，可以点击一个哭脸按钮让系统知道它出错了。如果用户阅读了一个系统未标记为有趣但自己却觉得好笑的页面，可以点击一个大笑按钮让系统知道。我们甚至可能想知道，与未被标记为有趣的页面相比，用户是否更倾向于阅读被标记为有趣的页面，因此我们可能会测量用户在标记为有趣的页面上花费的时间，以及未标记页面上的时间。

该插件会收集所有这些用户反馈和行为，并将其作为遥测数据发送回服务。添加遥测功能改进了整个智能实现，因为它让我们能够回答关于智能质量以及用户对整体系统感知的重要问题——即我们是否实现了总体目标。这也为我们进行改进奠定了基础。

因为当智能创建者查看遥测数据时，他们会发现初始模型在许多地方效果不佳。也许互联网上大多数有趣的内容都在图片中，而非文本中。也许某个国家的人觉得好笑的东西，另一个国家的人却并不觉得有趣。诸如此类。

智能创建者会花一些时间研究遥测数据；他们可能会爬取一些初始系统出错的页面，并构建一些新模型。然后，他们会得到一个比原始模型更优的模型，并希望将其推送给用户。

智能实现必须处理这个问题。一种选择是发布一个包含新模型的全新版本插件——Funny Finder v2.0。但第一版的用户需要自行找到这个新插件并选择安装。大多数用户不会这么做。即使有用户安装，也可能需要很长时间。这会导致智能更新缓慢（甚至无法更新），并降低了智能创建者工作的潜力。此外，智能可能变化很快：也许每周、每天、甚至每小时多次变化。除非实现能够定期且可靠地将新智能交付给用户，否则智能系统就不会很智能。

因此，实现方案可能会升级插件以支持自动更新。或者更优的做法是，修改插件使其仅更新模型（本质上是数据），而保持其余代码不变。插件会定期检查服务器，判断是否有新的智能内容，并进行下载。

很好。现在，实现方案运行智能、对其进行评估并更新。此时，服务于智能的代码量可能已经超过了智能本身：任何智能系统中，实现部分都占据了相当大的比重。这个版本的系统是完整的，它连接了用户与智能，使用户只需通过使用系统并提供反馈，就能从智能中受益并改进它。

但有些内容确实不好笑。有些内容令人反感、可怕。我们真的、真的不希望系统犯下那种将高度冒犯性内容标记为“好笑”的错误。

因此，或许可以让用户报告系统犯下的严重错误。在用户体验中增加一个新按钮，将关于冒犯性页面的遥测数据发送回我们的服务。

也许我们可以构建一个小型工作流，并雇佣一些人工来验证用户报告的冒犯性网站是否确实糟糕（而不是某种“喜剧战争”，即用户互相举报对方的内容）。这样会得到一个“真正、绝对不好笑”的网站列表。实现方案需要确保客户端能尽快获取此列表的更新。这个列表可以在模型更新时同步更新。或者，如果这样不够快，插件需要更主动地检查此列表，并将其包含的智能与模型输出的智能结合起来。

因此，现在插件被更新了：每次访问新页面时，它在运行本地模型的同时，还会发起一次服务调用。然后，它将这两种智能（基于服务器的智能和基于客户端的智能）的结果结合起来。如果服务器判定某个网站“真正、绝对不好笑”，那么无论客户端模型如何判断——该网站就是不好笑。

到了这个阶段，智能的创造者们会有各种想法，来构建无法在插件中运行的更好模型。也许新想法无法放在客户端，因为它们需要太多内存。也许它们无法放在客户端，因为它们需要外部查询（例如，语言翻译服务），这会给插件带来过大的延迟。也许插件需要在 CPU 资源严重受限的环境中运行，比如手机，而智能创造者只是想要更多的性能余量。

这类智能可能无法在客户端运行，但在服务的后端却可能完全适用。例如，当大量用户开始访问一个新网站时，后端可以察觉到。它可以爬取该网站。它可以运行数十种不同的算法——专门处理图像的、寻找特定类型幽默的、针对不同语言或文化调整的——并以某种方式将输出结果发送给客户端。

因此，现在插件正在整合来自多个来源的智能——一些来自云端，一些由自身执行。它正在管理体验。它正在衡量用户与智能交互的结果，并收集数据用于改进。等等。

并非每个智能系统的实现都需要所有这些组件。也并非每个智能系统都需要将这些组件实现到相同的程度。本书的这一部分将提供一个基础，帮助您了解何时以及如何投资于各种组件，以便您的智能系统有最大机会高效地实现其目标。

## 智能实现的组成部分

智能实现可以非常简单，也可以非常复杂。但每个智能系统的实现都必须解决一些关键功能，它们是：

*   在运行时执行智能并点亮体验。
*   摄取新的智能，进行验证，并将其部署到需要的地方。
*   监控智能（及用户结果），并获取改进系统所需的任何遥测数据。
*   为智能创造者提供支持。
*   提供控制手段来编排系统，以可控的方式演进系统，并处理错误。

### 智能运行时

智能必须被执行并与用户体验相连接。

为了执行智能，系统必须收集交互的上下文，即智能做出良好决策所需考虑的所有因素。这可能包括：用户正在做什么；用户最近做了什么；相关传感器显示什么；用户在屏幕上正在看什么；任何可能与智能决策相关的内容。

上下文必须被打包、转换，并呈现给代表智能的模型（或多个模型）。上下文与模型的结合会产生一个预测结果。运行时可以完全在客户端，也可以在客户端和服务之间进行协调。然后，必须利用预测结果来影响系统，点亮体验——创造影响力。

### 智能管理

当新的智能可用时，必须将其摄取并交付到需要的地方。例如，如果智能是在公司总部的实验室中创建的，而运行时需要在全美国的烤面包机上执行该智能，那么智能管理系统必须将智能分发到所有烤面包机。或者，智能可能在服务中运行。或者，它可能部分在后端运行，部分在客户端运行。智能可以驻留在许多地方，各有优缺点。

在此过程中，智能需要经过验证，以确保它不会做出（太）疯狂的事情。而且，智能系统通常依赖不止一个智能来源。这些可能包括多个模型、启发式规则和错误覆盖。这些必须被整合，并且它们的组合需要经过验证和交付。

### 智能遥测管道

获取正确的监控和遥测数据，是产生能够正确运行并随时间改进的智能的基础。

有效的监控和遥测包括：了解智能在哪些上下文中运行，以及它给出了哪些类型的答案。它包括了解智能产生了哪些体验，以及用户如何响应。一个有效的遥测系统将获取适当的数据，以培育出新的、更好的智能。

在大型智能系统中，遥测和监控系统会产生大量数据——非常大量。因此，智能实现必须决定观察什么、采样什么，以及如何消化和总结信息，以便在智能系统的各个部分之间实现智能的创造和编排。

### 智能创建环境

要使智能系统成功运行，运行时、交付、监控和智能创建之间需要高度协调。例如，为了生成准确的智能，智能创建者必须能够精确重现运行时发生的情况。这意味着：

*   遥测数据必须捕获与运行时相同的上下文（关于用户正在做什么、内容、传感器输出等信息）。
*   智能创建者必须能够以与运行时完全相同的方式处理此上下文。
*   智能创建者必须能够将遥测中出现的上下文与用户从交互中获得的最终结果（无论好坏）联系起来。


当智能创建者希望创新其模型所检查的信息/上下文类型时（他们必然会这样做；这被称为特征工程，是智能创建过程的关键部分），这可能会变得困难。当监控系统未能准确收集正确的信息，导致运行时与智能创建者所能看到的内容不匹配时，这可能会变得困难。当智能在与智能创建设备不同类型的设备上执行时，这可能会变得困难。也许运行时拥有与智能创建环境不同的协处理器、不同的显卡或不同版本的数学库。

其中任何一个问题都可能导致故障。

智能实现将通过为智能创建者提供尽可能高的一致性，来创建一个缓解这些问题的环境。

### 智能编排

智能系统需要被编排。

*   如果系统进入不良状态，需要有人将其恢复。
*   如果系统开始犯严重错误，需要在调查根本原因的同时有人进行缓解。
*   随着问题、智能和用户群的发展，需要有人能够掌控局面，调整智能和体验以达到预期结果。

例如，如果智能创建产生了一个糟糕的模型（并且没有任何检查发现它），该模型可能会开始给客户带来糟糕的体验。智能编排团队应该能够通过遥测数据快速识别性能退化，将问题追踪到特定模型，并禁用该模型或将其回滚到之前的版本。

如果情况足够糟糕，智能编排者可能需要关闭整个系统，而实现和体验应能优雅地响应。

为编排智能系统提供良好的可见性和工具，能让智能创建者更有信心地行动，承担更大的风险，并更快地改进。

## 总结

智能系统需要被实现，以便将智能与客户连接起来。这包括：

*   执行智能并点亮智能体验。
*   管理智能，将其部署到需要的地方。
*   收集关于智能如何运行以及用户如何响应的遥测数据（并用于改进智能）。
*   支持那些将要创建智能的人员，允许他们以与用户完全相同的方式与上下文交互。
*   帮助编排智能系统在其生命周期中的运行，控制其组件，处理错误等。

智能系统不同于传统程序，传统程序完成后即可实现、交付并弃之不顾。智能系统更像是一种需要持续运行并随时间改进的服务。智能系统的实现正是实现这一目标的平台。
