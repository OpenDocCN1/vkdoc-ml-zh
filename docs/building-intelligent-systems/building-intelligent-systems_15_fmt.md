# 12. 智能运行时

智能运行时将智能付诸行动。它负责与智能系统的其余部分交互，收集执行系统智能所需的信息，加载和解释智能，并将智能的预测结果连接回系统的其余部分。

从概念上讲，智能运行时可能看起来像这样：

```python
Intelligence theIntelligence =
InitializeIntelligence(,
,
);
Context theContext =
GatherContext(,
,
,
,
);
Prediction thePrediction =
ExecuteIntelligence(theIntelligence, theContext);
UpdateTheExperience(thePrediction);
```

原理上很简单，但像大多数好东西一样，在实践中可能需要相当大的复杂性。

本节涵盖智能运行时将处理的主要元素：

- 收集上下文。
- 构建特征。
- 加载模型。
- 在上下文/特征上执行模型。
- 将生成的预测结果与体验连接起来。

## 上下文

智能运行时中的上下文包含智能体可能用于决策的所有数据。例如：

- 如果智能系统试图判断洒水系统是否应该运行，上下文可能包括：
    - 自上次洒水以来的时间长度。
    - 未来几天的天气预报（是否会下雨）。
    - 过去几天的降雨量。
    - 用户拥有的景观类型。
    - 当前时间。
    - 温度。
    - 湿度。
    - 等等。
- 如果智能系统正在图像中寻找猫，上下文可能包括：
    - 原始图像数据（像素的 RGB 强度）。
    - 关于图像捕获方式的元数据（曝光度、帧率、时间、缩放倍数）。
    - 图像来源的位置。
    - 等等。
- 如果智能系统试图判断用户是否应该离开电脑休息一下，上下文可能包括：
    - 自上次休息以来的时间。
    - 用户休息后进行的活动（击键次数和鼠标移动次数）。
    - 用户活跃程度的指示。
    - 距离用户下一次会议的时间（根据其日历）。
    - 用户当前正在交互的应用程序名称。
    - 等等。

上下文可以是任何计算机可处理的信息，例如 URL、来自某个嵌入式设备的传感器读数、数字图像、电影目录、用户过去行为的日志、一段文本、医疗设备的输出、商店的销售收据、程序的行为等等。

这些都是在决定智能系统应该做什么时可能有用的信息。事实上，上下文通常是智能体实际用于决策的信息的超集。

一个好的上下文应该：

- 包含足够的信息，使智能体能够有效运作。
- 包含足够的信息，使智能体能够成长和适应。
- 包含足够的信息，使智能系统的编排者能够追踪错误。
- 在运行时能够高效地收集，以供智能体调用。
- 足够紧凑，可以包含在遥测数据中。

显然，这里存在权衡。更完整的上下文为智能体提供了更多潜力，但也可能遇到工程和运营上的限制，需要额外的 CPU 和内存使用以及网络带宽，并引入延迟和增加数据量。

## 特征提取

收集这些上下文变量可能需要付出相当大的努力。但这并非过程的终点。还有另一层代码将这些变量转换为智能体所需的表示形式。这额外的一层通常被称为“特征提取”或“特征化”，是机器学习系统中的常见部分。

这对智能体实现至关重要，原因有很多：

- 从上下文生成特征的代码需要在运行时执行。也就是说，它需要高效且可靠。
- 这段代码通常技术性强、计算开销大、涉及数学运算，并且对于没有丰富数据处理经验的人来说不够直观。
- 智能体的创建者会希望不断更改这段代码的功能；事实上，他们可能需要定期更改它，以持续发展智能体。
- 这段代码与智能体紧密耦合，特征提取代码和智能体（模型）必须保持同步——用于构建智能体的特征提取代码的确切版本，在运行时执行智能体时也必须使用。

由于这些因素，特征提取必须仔细规划。一些最佳实践包括：

- 为特征提取代码准备广泛的测试集。这应包括：
    - 对提取器进行单元测试。
    - 性能测试，以确保代码满足 CPU 和 RAM 要求。
    - 定期（可能是每天，或每次签入时）针对一组已知上下文执行特征提取代码，并将输出与已知基准进行比较的测试。任何输出变化都应由工程师和智能体创建者检查，以确保符合预期。
    - 一项测试，确保运行时的特征提取代码（当用户与之交互时）与智能体创建环境中的代码（当用于创建模型时）执行完全相同的操作。
- 在智能体和特征提取代码中编码版本信息，并让运行时验证它们是否同步。
- 能够脱离整个应用程序来更改特征提取代码；例如，通过每次模型更新时发送新版本的特征提取代码。
- 制定一个生命周期，将特征提取的变更从智能体创建者转移到工程师，再到部署。该生命周期应允许智能体创建者快速评估变更，并确保部署给用户的代码质量高。

## 模型

模型是智能体的表示形式（我们将在后续章节讨论表示形式的选择）。现在，将模型想象成一个数据文件。在某些智能系统中，模型每隔几天就会更改一次。在另一些系统中，它们每隔几分钟就会更改一次。

更改频率将取决于以下因素：

1.  系统获取足够数据以改进模型的速度。
2.  构建新模型所需的时间。
3.  分发新模型的成本。
4.  相对于成功标准，变更的必要性。

通常，模型的更改速度会比更大的程序快得多。一个高效的运行时应该：

- 允许轻松更新模型（即，无需重启整个系统）。
- 确保其使用的模型是有效的，并且所有组件（特征提取器、模型、上下文）都保持同步。
- 能够轻松地从模型错误中恢复（通过回滚到以前的版本）。

模型的一个关键考虑因素是它们在磁盘和 RAM 中占用的空间量。如果不加控制，机器学习可能会产生相当大的模型。但如果有需要，总是可以在模型大小和准确性之间进行权衡。

## 执行

执行模型是指基于上下文（及相关特征）请求模型做出预测的过程。

在最简单的情况下，当只有一个模型且该模型位于客户端时，执行模型可以简单到将特征加载到数组中，然后调用现成的模型执行引擎函数。市面上有能够执行机器学习所能构建的几乎所有类型模型的库，在大多数情况下，这些库完全够用——因此，大多数时候你甚至无需编写太多代码就能加载和执行模型。

当然，在某些情况下，这些库并不适用。例如，当内存或 CPU 受限时；或者当执行发生在具有特殊硬件（如 GPU 或 FPGA）的设备上，而库无法利用这些硬件时。

另一种执行形式涉及在服务器上运行的模型。在这种情况下，客户端需要打包上下文（或特征）的某种（紧凑）表示形式，将其发送到服务器，并等待响应，同时处理所有必要的协调工作，以妥善应对调用延迟，避免导致糟糕的用户体验。

当系统包含多个模型时（这很常见），执行过程需要运行每个模型，收集其结果，并将它们组合成最终答案。实现方式有很多种，包括：

- 对结果取平均值。
- 取最高（最确定）的结果。
- 根据上下文的某些规则选择信任哪个模型（例如，一个模型在 90210 地区对房价预测很准，但在其他地方表现糟糕；另一个模型适用于公寓，但不适用于独栋住宅）。
- 使用一个模型来组合其他模型的输出。

第四部分“创造智能”中的章节将更详细地讨论模型组合，以及这些方法（及其他方法）的优缺点。

## 结果

执行智能会得到一个答案。也许智能输出一个 0.91，这表示其讨论的内容有 91%的概率。实现必须利用这个结果来影响智能体验将采取的行动。例如，它可以将该值与阈值进行比较，如果值足够高（或低），则触发提示、自动化某些操作或注释某些信息——无论智能体验想要做什么。

### 智能的不稳定性

直接使用智能的原始输出可能存在风险，因为智能本质上是不稳定的。例如：

拍摄一张奶牛的数码照片。使用奶牛检测模型预测图像中包含奶牛的概率，输出可能很高，比如 97.2%。

现在等一天。后端系统有了新的训练数据，构建了一个新的奶牛检测模型，并将其分发到运行时。将更新后的模型应用于同一张奶牛图片，概率估计值几乎肯定会不同。差异可能很小，比如 97.21%（相比原来的 97.2%），也可能相对较大，比如 99.2%。新的估计值可能更准确，也可能更不准确。但不同版本的智能之间，估计值极不可能完全相同。

上下文的细微变化也可能产生类似影响。例如，将相机对准一头奶牛，尽可能快地连续拍摄两张数码照片。对人类来说，奶牛在两幅图像中看起来一样，背景看起来一样，光线看起来也一样——“奶牛检测”模型应该对第一张图像和第二张图像输出相同的概率估计。这是人类的看法。

但对于模型来说，这些图像可能看起来非常不同：数字传感器会引入噪声，而图像之间的噪声分布会不同（产生人眼难以察觉的微小斑点）；奶牛可能在一张图像中眨了眨眼，而在另一张中没有；风可能吹过，改变了树叶阴影的位置；相机的位置可能发生了极其微小的变化；相机的自动对焦或曝光校正可能对图像做了略微不同的处理。

由于所有这些原因，智能可能对这两张图像做出不同的估计。可能一张是 94.1%，另一张是 92.7%。

这种变化对于由此产生的智能体验来说可能无关紧要，但也可能至关重要。

试图假装机器学习系统中不存在不稳定性，可能会导致效果较差（甚至糟糕）的智能体验。

### 智能 API

为了解决智能输出的不稳定性，通常将智能封装在一个接口后面会很有帮助，该接口只暴露实现系统目标所需的最少信息：

*   处理概率时，考虑舍弃一些精度：将 92.333534%四舍五入为 90%。
*   考虑将概率转换为分类：不要说“有 45%的概率存在一头奶牛”，而是说“没有奶牛”。
*   考虑对预测进行量化：不要说“图像中坐标(14,92)处有一头奶牛”，而是说“图像左侧有一头奶牛”。

实现这些类型转换所需的阈值和策略与智能紧密耦合，应在每次更新模型时一并包含在内。

虽然这些做法确实有助于使模型输出更稳定，并提供一定程度的模型内部封装，但它们并非完美无缺。例如，假设奶牛检测器在一帧图像中有 81%的把握认为存在一头奶牛。模型的阈值设定为 80%。因此，系统创建了一个“此处有奶牛”的分类，并点亮了一个用户界面元素。

然后，在下一帧图像中，奶牛检测器只有 79.5%的把握认为存在一头奶牛，用户体验元素闪烁消失。这看起来可能非常糟糕。

一个设计良好的 API，结合一个旨在最小化缺陷的体验设计，两者都是打造有效智能体验所必需的。

## 总结

智能运行时负责：收集系统上下文；将此上下文转换为与智能兼容的形式；执行构成智能的各种组件；组合智能结果，并在智能与体验之间创建良好的接口；以及利用智能的输出来影响用户体验。

智能运行时需要处理的一些关键组件包括：

*   **上下文**，包括在智能系统中做出良好决策相关的所有信息。
*   **特征**（以及特征提取代码），将上下文转换为与包含系统智能的特定模型兼容的形式。
*   **模型**，代表智能，通常包含在数据文件中，这些文件在智能系统的生命周期内会相对频繁地变化。
*   **执行引擎**，在特征上执行模型并返回预测结果。有许多优秀的库支持模型执行，但通常需要对这些库进行封装以组合智能；有时需要针对独特的执行环境进行替换。
*   **结果**，即智能的预测结果。最佳实践是保持原始结果的私密性，并创建一个智能 API，该 API 仅暴露为智能体验提供支持所需的最少信息，同时能够稳健地应对随时间发生的变化。

一个有效的智能运行时将：易于追踪错误；在运行时中的执行方式与在智能创建环境中的执行方式相同；支持对模型和特征提取进行轻松更改；并使系统的各个部分难以不同步。
